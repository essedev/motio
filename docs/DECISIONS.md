# Decisions

Each entry: the decision, why, and what would make us revisit it. Newest last.

## D-001 Licence: Apache-2.0 (2026-11-22)

Matches the code we may port (HyperFrames) and adds a patent grant. MIT would not change the licence of ported Apache code anyway.

## D-002 FFmpeg is a system dependency (2026-11-22)

The engine runs the `ffmpeg` and `ffprobe` found on `PATH` (or configured) as separate processes; `doctor` and every render check the minimum version and the encoders the output needs, and the render metadata records the version. No binary on npm: common static builds are GPL because of x264, and `libfdk_aac` cannot be redistributed. Reproducibility comes from the official container image, which pins one build. Revisit if installation friction proves to be the main adoption barrier: a pinned download can be added as an opt-in package. (Done: the optional `@motiojs/ffmpeg` package, D-065.)

## D-003 Vite bundles user projects (2026-11-22)

One tool for the dev page and the render bundle, a plugin API that fits the compat alias, the standard in the React ecosystem. Remotion's `webpackOverride` has no equivalent; the migration guide maps the common overrides and `doctor` flags projects that define one.

## D-004 Name: Motio (2026-11-22)

Entry package `motio`, CLI `motio`, other packages under `@motiojs/*` because the `@motio` npm scope belongs to an existing organisation.

## D-005 Time model: frame model by default, virtual clock opt-in (2026-11-22)

The spike rendered eight fixtures (frame-driven, state set in an effect, CSS keyframes, Web Animations, a `requestAnimationFrame` canvas loop, a `setInterval` counter, `Math.random` and `Date.now` in render) over 60 frames in five orders: sequential twice, reverse, shuffled, and a fresh page per frame. Agreement with the fresh page, out of 60 frames:

| Fixture | No shim | No shim + animation seek | Shim + animation seek |
|---|---|---|---|
| Frame-driven | 60 | 60 | 60 |
| State set in effect | 60 | 60 | 60 |
| CSS keyframes | 0 | 60 | 60 |
| Web Animations | 0 | 60 | 60 |
| rAF + `performance.now` | 0 | 0 | 60 |
| `setInterval` counter | 2 | 2 | 1 to 60, order dependent |
| `Math.random` | 0 | 0 | 60 |
| `Date.now` | 0 | 0 | 60 |

Conclusions:
- `flushSync` plus the passive effects of a sync render are enough for effect-driven state; the shim did not disturb React in these fixtures.
- Seeking `document.getAnimations()` makes CSS and Web Animations deterministic without any clock patching, so it is on in both models.
- The shim fixes stateless clock reads in any order, but state accumulated by timers depends on where the page started, which contradicts "any frame, any order".

So the default is Remotion's model (the frame is the only source of truth, no clock patched, any order), plus animation seeking. The virtual clock is opt-in for third-party libraries that read the clock, with contiguous ascending ranges per page. This keeps the default as safe as Remotion and takes the shim off the critical path. The adversarial review reached the same recommendation independently. Revisit if a large share of real projects need the virtual model.

## D-006 Capture: screenshot path, JPEG 80 by default (2026-11-22)

On an Apple M5, chrome-headless-shell 158, software GL, the spike measured per page: `seek` 4.5 ms; `Page.captureScreenshot` about 49 to 64 ms per frame whether PNG, JPEG 90 or JPEG 80, at 720p or 1080p; piping to libx264 (`veryfast`, CRF 18) adds almost nothing. Capture latency, not encoding or format, bounds a single page, so throughput comes from concurrency (see D-007 for the measurement) and, on Linux, from BeginFrame, to be measured in the container in M1. JPEG 80 stays the default for opaque output for parity with Remotion; PNG for alpha and lossless.

## D-007 Page pool: one browser process per page (2026-11-22)

Measured at 1080p, JPEG 80, 240 frames, Apple M5 with 10 cores: 1 page 9.5 fps; 2 pages 19.5 (one browser) against 20.6 (two browsers); 4 pages 31.7 against 33.6; 8 pages 33.3 against 54.7. Pages sharing one browser process saturate around 33 fps (one GPU and compositor process), while separate processes keep scaling. The pool therefore gives each page its own browser process, which also confines a crash to one page. Revisit if memory per process limits concurrency on small machines.

## D-008 Compatibility target: remotion@4.0.545 (2026-11-22)

The latest published version when work started. Every compatibility claim and oracle recording refers to it; moving it is an explicit change that re-records the oracle.

## D-009 Oracle recordings are made by the author as an individual (2026-11-22)

Recording reference values and frames means running Remotion. Remotion's licence is free for individuals; recordings made for a company would need a company licence. The recordings are produced by the project author as an individual for this personal open-source project, at the pinned version, with the oracle installed outside the workspace. Confirmed by the author on 2026-11-24: the recordings were made by the author as a private individual, for tests of this personal project.

## D-010 Kinetograph: ideas only (2026-11-22)

Its licence could not be verified and its easing code has unattributed provenance, so no code is ported from it. Easing and the other pure functions are written from public formulas and checked against the oracle.

## D-011 Milestone order: compat breadth before the production project (2026-11-22)

A real production project almost certainly uses transitions, Google Fonts, Zod and Tailwind, so the breadth milestone comes before it. Media and the Player come after breadth because the first renders and templates are mostly graphics.

## D-012 Tooling (2026-11-22)

- `tsc -b` with project references builds and type-checks every package: libraries emit ESM with declarations and need no bundling, and references enforce package boundaries. Revisit with tsdown if a package needs bundling.
- Biome for lint and format, Vitest for tests (Node, jsdom and a serial integration project with the real Chrome and FFmpeg), Playwright only for the Player.
- TypeScript 7 (native compiler), pnpm workspaces, ESM-only, Node 22 or later.

## D-013 BeginFrame capture on Linux, sandbox off only inside containers (2026-11-22)

Measured in the pinned image (`docker/`, linux-arm64, Debian trixie, chrome-headless-shell 158) at 1080p PNG, one page, 120 frames: `Page.captureScreenshot` 72.6 ms per frame, `HeadlessExperimental.beginFrame` with a screenshot 19.0 ms per frame (3.8 times faster), a screenshot on every frame. Decoded pixels are identical between the two paths on every deterministic fixture (frame-driven, effect state, CSS, Web Animations); only the fixtures that read the real clock differ, as expected without the shim. BeginFrame becomes the default capture path where the start-up probe succeeds (Linux), with the screenshot path as fallback and reference; scheduled in M2.

Docker's default seccomp profile blocks the user namespaces Chrome's sandbox needs. Inside the image the renderer passes `--no-sandbox` (set by `MOTIO_CHROME_NO_SANDBOX=1`), the container being the isolation boundary; outside containers the sandbox stays on.

## D-014 Audio mixer: a separate package, volume applied on time (2026-11-22)

The mixer lives in `@motiojs/audio` (Node), used by the renderer, so it is tested on its own against the media oracle. Sources are decoded by FFmpeg (trim, pitch, tempo, resampling), then placed, enveloped and summed in Node in float, and encoded once. A mono source is duplicated at full level: FFmpeg's default upmix lowers it by 3 dB, which Remotion does not do.

Against `fixtures/media`, click times match within 1 ms (offset, trim, volumes, ramp) and within 2 ms for `playbackRate` 2; constant volumes match within 0.01. Remotion applies volume changes about 1.5 frames late (up to 2.5 on the ramp); Motio applies the per-frame volume on time and does not reproduce the lag until its rule is known, because a 50 ms envelope offset is inaudible in practice and copying an unexplained artefact would be guesswork. Clicks inside that window are excluded from the peak comparison. Revisit if the rule is identified black-box.

## D-015 Embedded video: extracted frames, selection rule per component (2026-11-22)

`@motiojs/video-frames` selects the source frame from the packet timestamps of the stream (no decoding, so variable frame rate works) and extracts it as PNG with an accurate FFmpeg seek, batching following frames and caching them in an LRU with request deduplication. Against `fixtures/media`, the `floor` rule reproduces Remotion's `OffthreadVideo` and `@remotion/media` `Video` sequences exactly (24, 30, 59.94 and 60 fps sources, `playbackRate` 2, `trimBefore` with a `Sequence` offset).

Remotion's HTML5 `Video` is not frame-exact in renders: its recording jumps back to stale frames on 7 of 60 frames and rounds inconsistently on fractional positions, agreeing with the `nearest` rule on 48 of 60. Motio renders the HTML5 `Video` through the same extraction path with the `nearest` rule, which is deterministic and matches Remotion wherever Remotion is itself consistent. Revisit if a project depends on the native element during render (for example drawing it to a canvas), which the M3 `Video` ref design must cover.

## D-016 HTML5 `Video` keeps the native element in renders (2026-11-22, supersedes the HTML5 part of D-015)

Measured in chrome-headless-shell 158 with the frame-stamped sources: a native `<video>` seeked to the middle of the selected frame's interval (`(k + 0.5) / fps` for constant frame rate, the midpoint between the frame's timestamp and the next one in general), waiting for `seeked`, shows exactly frame k in 456 of 456 seeks (24, 59.94 and 30 fps, random order with backward seeks). `requestVideoFrameCallback` does not fire in headless-shell without compositor frames, so `seeked` is the readiness signal. Seeking only works when the server answers HTTP `Range` requests: without them every seek shows frame 0, so the renderer's static server must support `Range`.

So the HTML5 `Video` renders the real element, seeked to the midpoint of the frame chosen by the `nearest` rule from timestamps the host provides (D-015). Refs keep pointing at an `HTMLVideoElement`, and drawing it to a canvas works. `OffthreadVideo` and `@remotion/media` `Video` keep the extraction path, which also covers codecs Chrome cannot decode (ProRes, HEVC on Linux).

## D-017 Google Fonts: generated modules, committed (2026-11-23)

`@motiojs/google-fonts` has one generated module per family (`@motiojs/google-fonts/<ImportName>`, exporting `fontFamily`, `getInfo`, `loadFont` and, for variable families, `loadVariableFont`) plus `getAvailableFonts()`. `scripts/generate.ts` reads Google's public font metadata and the CSS2 API (static and variable faces, per subset); the set of families is the one `@remotion/google-fonts` 4.0.545 lists, recorded from its public `getAvailableFonts()`, so import paths match one for one. All 1,848 families generate; the recorded samples match in exports, styles, weights, subsets, unicode-range subsets and variable axes. File URLs differ from Remotion's (Google varies them by user agent) and are not compared.

The generated modules (about 10 MB of source) are committed and excluded from lint: builds stay offline and reproducible, and a regeneration shows up as a reviewable diff. Revisit if regeneration churn makes the history heavy; the alternative is generating at publish time.

## D-018 Chunk assembly: MPEG-TS chunks, concat without re-encoding (2026-11-23)

`@motiojs/distributed` plans contiguous chunks (optionally aligned to a GOP) and assembles video-only MPEG-TS chunks with FFmpeg's concat demuxer and stream copy, then muxes the audio rendered once (D-014). Tested with frame-stamped chunks encoded independently by libx264 with 3 B-frames: 240 frames in chunks of 37 at 30 and 29.97 fps decode to exactly frames 0 to 239, once each, in order, and audio muxes alongside. MPEG-TS is used because MP4 chunks carry edit lists for B-frame delay that the concat demuxer does not apply, which shifts or duplicates frames at boundaries. Next: the renderer gains a chunk output mode (frame range to MPEG-TS) and a local worker adapter implements `ChunkWorker`.

## D-019 Alpha output recipes (2026-11-23)

Measured with RGBA PNG frames (alpha gradient plus a half-transparent box) encoded and decoded back to RGBA:

| Recipe | Max alpha error | Max colour error on opaque pixels |
|---|---|---|
| ProRes 4444: `prores_ks -profile:v 4444 -pix_fmt yuva444p10le -vendor apl0` | 1 | 0 |
| VP9 lossless: `libvpx-vp9 -pix_fmt yuva420p -auto-alt-ref 0 -lossless 1` | 1 | 0 |
| VP9 lossy, `-crf 4 / 10 / 15 / 20 / 31 -b:v 0` | 2 / 3 / 3 / 7 / 12 | 0 |

`-auto-alt-ref 0` is required for VP9 alpha. Reading the alpha of a VP9 WebM needs the `libvpx-vp9` decoder (`-c:v libvpx-vp9` before `-i`): FFmpeg's native VP9 decoder drops the alpha plane, which also applies to `@motiojs/video-frames` when the source is a transparent WebM. The M5 alpha criterion therefore reads: ProRes 4444 and lossless VP9 within 1 code value of the PNG frames; lossy VP9 within the error measured here for its CRF.

## D-020 GIF output recipe (2026-11-23)

GIF output encodes the captured frames with a palette built for the clip: `-filter_complex "[0:v]split[a][b];[a]palettegen=max_colors=256:stats_mode=full[p];[b][p]paletteuse=dither=none"`. On a 2 s test signal this gives 41.3 dB PSNR against the source frames, with every frame present. `everyNthFrame` selects frames before encoding and divides the frame rate (every 3rd frame of 30 fps gives 20 frames at 10 fps for 60 inputs). Remotion's `numberOfGifLoops` maps to FFmpeg's `-loop`: `null` (loop forever) is `-loop 0`, `0` (play once) is `-loop -1`, which omits the NETSCAPE loop extension, and `n` (repeat n times) is `-loop n`, checked in the written loop extension. Dithering is off by default for deterministic, flat output; an option can enable it later.

## D-021 `viteOverride` replaces `webpackOverride` (2026-11-23)

`bundle()` rejects `webpackOverride` with an error that points to `viteOverride`, a function that receives and returns the Vite configuration (D-003). `remotion.config.ts` setters with no equivalent (`overrideWebpackConfig`) record a warning instead of throwing, and `enableTailwind` is recognised and turned into `@tailwindcss/vite` (v4) or PostCSS (v3).

## D-022 Player browser tests use puppeteer-core (2026-11-23, supersedes the Playwright part of D-012)

The Player's real-browser tests drive the pinned chrome-headless-shell with puppeteer-core, already used by the renderer, instead of Playwright: one browser binary and one driver for the whole repository, no extra browser download. Playwright remains an option if cross-browser Player tests are added.

## D-023 `useWindowedAudioData` is approximated (2026-11-23)

For WAV files the loaded windows, `resultId`, `dataOffsetInSeconds`, sample rate, duration and errors match Remotion, but Remotion repeats one sample at each window boundary (its windows run 1 to 3 samples long) while Motio's windows tile the file exactly; on windowed data `visualizeAudio` then differs by up to 0.042 and `visualizeAudioWaveform` by up to 0.0028. Non-WAV files are decoded whole at 48 kHz and sliced. Every other `@motiojs/media-utils` function matches exactly or within 1e-12 (`packages/media-utils/COMPAT.md`). Motio keeps the exact tiling: duplicating a sample is an artefact, not a contract.

## D-024 M1 closed (2026-11-23)

Every M1 criterion in `ROADMAP.md` is backed by a committed test that passes in `make check`: pure functions against the oracle (exact or within 1e-12), frame stamps over 3,000 frames at concurrency 1, 4 and 8 in random order, the React fixtures, determinism across runs, orders and concurrencies, the colour round trip with `ffprobe` checks, the 28 fixture stills against Remotion (SSIM at least 0.9975, PSNR at least 45.9 dB), and error codes with label and frame. An adversarial review of the M1 code found six defects (an asynchronous `cancelRender()` reported as a page error, `--frames` lists, `check determinism` never rendering in descending order, frames missing from crash errors, non-atomic stills, the default check concurrency on 1-thread machines); all are fixed with tests. The repository builds and renders from a clean `git archive` inside the pinned Linux image.


## D-025 Official templates: fetched at pinned commits, resolved from a parent package, compared at scale 1 (2026-11-23)

The M2 template proof (`fixtures/templates`) fetches each official template at a pinned commit into a gitignored cache and never commits its code: the templates carry no open-source licence (`UNLICENSED`, pointing to the Remotion License), and fetching the public repositories at test time needs none. The commits are the heads that go with `remotion@4.0.545`, not older revisions chosen to pass. "Zero edits" is read strictly: nothing is installed into the template and no file changes; its imports resolve from `fixtures/templates/node_modules`, a workspace package that depends on `motio`, the mapped `@motiojs/*` packages and the third-party versions the templates pin, as a monorepo parent would. Reference stills are rendered at scale 1: at scale 0.5 Motio's and Remotion's rasterisation differ (both use a device scale factor; SSIM 0.982, PSNR 27 dB on a still that matches at 52 dB at scale 1), which would mix renderer differences into the template proof. Templates that cannot build yet stay in the suite as expected failures naming the missing symbol or package, and known still mismatches are listed with their cause; each of these tests fails once the cause is fixed.

## D-026 `motio dev`: a Player page served by Vite, with a render check (2026-11-23)

The preview page is its own browser package, `@motiojs/preview`, served by `startDevServer()` in `@motiojs/bundler`, which reuses `bundle()`'s settings (compat alias, React deduplication, env variables, Tailwind, `viteOverride`) and adds `@vitejs/plugin-react` for Fast Refresh, limited to the project's own files so Motio's packages never become refresh boundaries. Choices beyond the docs:

- The bundle context (`staticFile()` base and list, `process.env`) is set by a classic inline script in the page, not a module, because dependencies read `process.env` while they are evaluated; it is not frozen there, since Vite's client assigns its `define` values onto it. The public directory is served from `/` by a small static middleware with `Range` support (D-016), because Vite's public middleware cannot serve names containing `#`, which `staticFile()` encodes.
- The stage resets inherited CSS (`all: initial`) and applies the render page's zero-specificity `border-box` rule: with the page's line height inherited, preview and render of the CLI fixture scored SSIM 0.992; with the reset, 0.9999. The integration test requires 0.999.
- "Render still" goes through the real pipeline: the CLI passes the server a handler, so the bundler does not depend on the renderer. It rebuilds a production bundle only after a watched file changed, then runs `selectComposition` with the page's props and `renderStill` as PNG at scale 1, one request at a time; an aborted request cancels its render.
- An explicit `--port` is strict (`E_PORT_IN_USE`); `Config.setStudioPort()` or the default 3000 moves to the next free port. Nothing opens by default (Remotion's Studio opens a browser), `--open` does; agents and CI start servers more often than people do. `--json` prints one object as soon as the server listens and nothing after it, so stdout stays one JSON value; SIGINT, SIGTERM and SIGHUP close the server and remove the session's files.
- In the preview, `getRemotionEnvironment()` reports `isPlayer` (it is a Player page) and `getInputProps()` returns `{}`, while Remotion's Studio reports `isStudio` and returns `--props`; `--props` seeds the props editor instead. Revisit if projects branch on either in the preview.

## D-027 Google Fonts generated with the user agent that matches Remotion's files (2026-11-23, refines D-017)

Google's CSS2 API serves differently subset woff2 files per user agent, with different glyph metrics: the official Overlay template rendered a text box 2 px narrower than Remotion's because the generator used a recent macOS Chrome user agent. With a Windows Chrome 120 user agent Google returns exactly the files `@remotion/google-fonts` 4.0.545 references. The generator now uses it, all 1,848 modules are regenerated, and the tests require identical file URLs, unicode ranges and variable faces for every recorded sample.


## D-028 Mono sources upmix at -3 dB, as Remotion's output measures (2026-11-23, supersedes the mono part of D-014)

D-014 duplicated a mono source into both stereo channels at full level, from a comparison of the mixer's first channel with the oracle's clicks. But the media recorder decodes Remotion's output with `-ac 1`, FFmpeg's stereo downmix `(L + R) / sqrt(2)`, so the oracle peak (0.9155, the click's own amplitude in `clicks.wav`) is what a stereo output with each channel at -3 dB measures, the result of FFmpeg's default mono-to-stereo matrix (or of a mono output). Full-level duplication measured 1.2947 through the recorder's method, 41% louder than Remotion. The mixer now lets FFmpeg convert channel layouts with its default matrix, and the mixer test measures through the same downmix as the recorder; every click time and constant-volume peak still matches (D-014's tolerances). Stereo sources are unaffected.

## D-029 `@motiojs/media`: one package for the media of `remotion` and `@remotion/media` (2026-11-23)

The package root mirrors `@remotion/media` (`Video`, `Audio`, and `experimental_Video`, `experimental_Audio` as aliases), because the compat alias maps that package here. The `remotion` components are exported under their unambiguous names (`Html5Video`, `OffthreadVideo`, `Html5Audio`); `motio` re-exports them and adds `Video` and `Audio` as the former names of `Html5Video` and `Html5Audio`, which is what `remotion` 4.0.545 exports under those names. `AudioForPreview` and `getTargetSampleRate` are undocumented and not exported. `Img` stays in core: it needs nothing from the host, and moving it would change core's exports for no gain.

Choices beyond the docs:

- **One timeline model.** Every component wraps its media in a `Sequence` without layout whose child frame is the source position in composition frames (`trimBefore + elapsed * playbackRate`), so nesting, `Loop`, `Freeze` and premounting behave as for any sequence. `trimAfter`/`endAt` become a `durationInFrames`; when both limit the range the shorter wins. A loop without a finite range lasts the media duration rounded down to whole frames (Remotion's own `OffthreadVideo` looping recipe), read from the host in a render and from the element's metadata in a preview.
- **Volume callbacks** receive the frames elapsed since the media started, on its parent's timeline (restarting per loop iteration with `loopVolumeCurveBehavior="repeat"`), and apply on time (D-014).
- **Renders.** `OffthreadVideo` shows the host's extracted frame in an `<img>` and the `@remotion/media` `Video` draws it into a `<canvas>` at the source's size with `objectFit` as CSS (both `floor`, D-015); the HTML5 `Video` keeps the native element (D-016). There is no fallback chain: FFmpeg decodes everything Mediabunny would hand to a fallback, so `onError` returning `"fallback"` only keeps the render going when `fallbackOffthreadVideoProps.onError` handles the error, as it would for `OffthreadVideo`. `toneFrequency` and `audioStreamIndex` apply in renders only; `effects` fail with a clear error.
- **Previews** use native elements for every component, including the `@remotion/media` ones (Remotion decodes those with Mediabunny into a canvas and Web Audio): they play on the real clock at the Player's rate times their own, seek when they drift beyond `acceptableTimeShiftInSeconds` (default 0.45 s), and take the component's volume times the Player's, clamped to 1. `@remotion/media` components hold the Player while buffering by default, the others with `pauseWhenBuffering`. `Html5Audio` borrows one of the Player's shared audio tags, which the Player unlocks on every play request; borrowing more than `numberOfSharedAudioTags` throws, as documented.

## D-030 Media service, audio pass and audio output (2026-11-23)

- **Media service.** Each render session starts a small HTTP server on 127.0.0.1 next to the bundle server, passed to the page as `RunContext.mediaBaseUrl` (protocol 2). Its routes take the media URL the page uses: `info` (duration, video size and frame count, audio streams), `frame` (the PNG of the source frame for a time and a selection rule, with or without alpha) and `locate` (the frame's index and the midpoint a native element must seek to). Frame selection runs on the host from packet timestamps (D-015), so the page never needs the timestamp list. A separate server instead of a route on the bundle server or Fetch interception: it works the same when `serveUrl` is a remote URL, and media on the bundle's origin is read from the bundle directory directly. Responses carry `Access-Control-Allow-Origin: *`, so extracted frames can be drawn to a canvas.
- **Audio intents per frame.** A component reports, on each frame it plays, the source position in composition frames, the cumulative playback rate, pitch, volume and stream. The renderer joins consecutive output frames into one segment while the position advances by exactly the rate; a seek, a loop restart, a mute or a gap starts a new one. This needs no component identity across pages (React's client ids count mounts), and two identical sources that differ only in volume play the same samples, so their order does not matter.
- **The audio pass.** Intents are collected from the frames the capture already seeks, and the frames it skips (`everyNthFrame`, audio-only codecs) are seeked without capturing. In the frame time model a frame's intents depend only on the frame, so this equals seeking every frame in a separate pass at a fraction of the cost. The audio covers every frame of `frameRange` (ranges concatenate as the video does) at the composition's fps; `muted` renders no audio and no track.
- **Output.** `codec` `h264` muxes AAC (default) or MP3; `mp3`, `aac` and `wav` (PCM 16-bit) render audio only. Remotion's table of audio codecs per container did not render in its docs, so this is the subset Motio can encode today; `preferLossless` picks PCM where the container allows it, which MP4 here does not. `audioBitrate` defaults to 320k as documented, `sampleRate` to 48000. With no audible source the track is omitted unless `enforceAudioTrack`, `separateAudioTo` or an audio-only codec asks for silence. AAC is encoded in the same FFmpeg run that muxes it, so the encoder delay stays compensated by the container (the WAV and MP4 renders of `audio-offset` correlate at a lag of 0 samples). Sources without the requested audio stream are skipped. `forSeamlessAacConcatenation` fails with a clear error until chunked renders need it (D-018 muxes the audio rendered once).

## D-031 Transparent edges of scaled layers: open, default compositing unchanged (2026-11-23)

Two template stills (OnlyLogo 20, Overlay 30) miss the thresholds only at the antialiased edges of a scaled element over a transparent background (PSNR 33 and 38 dB; on white the same frames match at 52 dB). Measured so far: the element has the same size in both renders (337.0 against 337.02 px wide); Remotion's edges carry a faint bilinear resampling halo (alpha 2 to 3 outside the edge) that Motio's do not. Ruled out: fonts (fixed separately, D-027), the Chrome patch version (Motio rendering with Remotion's own 158.0.8127.2 binary gives the same result), and the command line (observing the running process shows Remotion launches Chrome with the same GL and determinism flags, GPU compositing through SwiftShader). Compositing in software (`--disable-gpu-compositing`) reproduces Overlay exactly but moves the 3D `flip` transition from SSIM 0.9995 to 0.989, so the default stays GPU compositing through SwiftShader. Next lead: page-level differences in how the composition container is layered (a wrapper transform or layer that makes Chrome rasterise the scaled element at scale 1 and resample it). The two stills stay marked as known mismatches in `fixtures/templates/templates.json`.

## D-032 Throughput against Remotion: measured gap and the plan to close it (2026-11-23)

Head-to-head on the same machine (Apple M5, 10 cores), same compositions (`fixtures/compositions` motion and timeline, 60 frames rendered at scale 3 = 1920x1080), H.264 at CRF 18, muted, total wall time including browser start:

| Concurrency | Remotion 4.0.545 | Motio | Motio, `x264Preset: "ultrafast"` |
|---|---|---|---|
| 1 | 3.5 to 3.9 s | 5.4 to 6.3 s | |
| 4 | 1.4 to 1.9 s | 3.0 to 4.4 s | 2.9 s |
| 8 | 1.2 to 1.6 s | 3.7 to 4.7 s | 2.5 s |

Motio is 1.6 to 3 times slower today. Causes measured so far:

1. **Pool layout (revisits D-007).** On the real bundle at 1080p, seek plus JPEG capture alone reaches 63 fps with one browser per page and 77 fps with 8 pages in one browser; D-007 had measured the opposite on a trivial scene. Pages sharing one browser (or a few) should be the default, with the process-per-page layout as an option for crash isolation.
2. **Colour conversion of JPEG frames.** The exact path (JPEG YCbCr to 16-bit RGB to BT.709 YUV, accurate rounding) encodes at 70 fps offline and produces files 64% larger than a range-only conversion that keeps the BT.601 matrix (138 fps, 46.6 dB against the captured frames, against 48.4 dB for the exact path); Remotion's files are of the smaller kind and carry no colour tags. Candidate default: the range-only path tagged BT.601 (`smpte170m`), keeping the exact BT.709 path behind `colorSpace: "bt709"`.
3. **Remaining pipeline overhead.** Even with the encoder at `ultrafast`, the full render reaches about half the raw capture throughput: per-frame work in the renderer between capture and encoder (transfer, reorder buffer, backpressure, the media service and audio-intent collection added in M3) needs profiling.

A performance criterion is added to the roadmap: wall time at most Remotion's at concurrency 1, 4 and 8 on these compositions, measured by a committed benchmark script.

## D-033 BeginFrame capture in the renderer: probed, default on Linux, with a pre-frame (2026-11-23)

The renderer resolves `captureMethod` (a Motio option, `--capture-method`, `$MOTIO_CAPTURE_METHOD`) per session: `auto` launches the browser once with the BeginFrame flags of D-013 and keeps BeginFrame if a `HeadlessExperimental.beginFrame` returns a screenshot of the right size, else the screenshot path; macOS skips the probe (BeginFrame control is not available there). `begin-frame` forces the path and fails with `E_BEGIN_FRAME_UNSUPPORTED` where the probe fails; `screenshot` keeps the reference path. Listing compositions never probes. Measured in the pinned image (linux-arm64) and what the implementation needed beyond the spike:

- **Scale.** BeginFrame screenshots ignore the emulated device scale factor, so a BeginFrame browser is launched with `--force-device-scale-factor` set to the render's `scale` (identical pixels to the screenshot path at scale 2).
- **First frames.** The first BeginFrames after a navigation can return no screenshot while the compositor initialises; the capture retries up to 10 times before `E_CAPTURE_FAILED`.
- **No frames between captures.** Under BeginFrame control style, layout and `requestAnimationFrame` run only inside a frame. While any page call is in flight, frames without display updates are sent every 16 ms, so `requestAnimationFrame` keeps working; a seek that settles within 16 ms sends none. Before each captured frame, a frame without display updates runs style and layout, and the capture waits for the images, fonts and style sheets that frame requested (tracked through the Network domain, after a round trip through the page's main thread so the request events arrive first), repeating until a frame requests nothing. Without it, a CSS background image was missing from the first frame of every page, which `check determinism` caught.
- **Identity.** `packages/motio/src/begin-frame.integration.test.ts` captures every `fixtures/compositions` frame of `frames.json`, the first, middle and last frame of every `fixtures/media` composition (native and extracted video), the 30 frames of the CLI fixture (a CSS background image), 120 frame stamps in PNG and 30 in JPEG, the palette, effect-state and alpha fixtures with both paths: every decoded frame is identical. The frame-stamp test (3,000 frames at concurrency 1, 4 and 8, random order) passes with zero mismatches on the BeginFrame path, and the CLI's `check determinism` passes; at 512x288 it ran at 102, 146 and 186 fps against 20, 81 and 127 fps on the screenshot path (runs on a shared machine vary by about 30%).
- **Speed.** 240 frames at 1920x1080, one page: PNG 63.5 ms per frame with the screenshot path against 20.1 ms with BeginFrame (3.16 times faster), JPEG 63.4 against 17.5 ms (3.61 times). The pre-frame costs part of the 3.8 times D-013 measured without it.

Revisit if Chrome removes `HeadlessExperimental.beginFrame` from headless-shell, or if the pre-frame proves insufficient for a resource type it does not track (media elements are excluded because they stream).


## D-034 `Easing.spring`: validated lazily, two configurations throw instead of hanging (2026-11-23)

`Easing.spring(config)` follows remotion.dev/docs/easing (a spring measured over 30 frames at 30 fps) and the recordings: inside the segment it is `spring({ frame: t * 30, fps: 30, durationInFrames: 30, durationRestThreshold })`, at or before 0 it returns 0, at or after 1 it returns 1, and with `allowTail` it continues as the unstretched spring at frame `t * natural duration`. Like Remotion, the configuration is validated the first time the spring is evaluated inside (0, 1) or in its tail, not when the easing is created, so `Easing.spring({ damping: 0 })` only throws once used. The returned function carries `remotionShouldExtendRight`, set to the `allowTail` value, which `interpolate()` reads (D-035).

Two configurations never return in Remotion (the recorder gives up after 20 s, and in-process they leave later `Easing.spring` calls failing with `RangeError: Too many properties to enumerate`): `stiffness: 0` and `durationRestThreshold: 0`. Motio throws instead (`Spring stiffness must be greater than 0, ...` from `measureSpring()`, and `durationRestThreshold must be greater than 0 for Easing.spring(), ...`). `measureSpring()` now throws its threshold errors as `TypeError`, as Remotion does; the messages are unchanged.

## D-035 `interpolate()` non-numeric outputs: one numeric core over vectors, rules completed black-box (2026-11-23)

The documented output types of `interpolate()` (CSS `scale`, `translate`, `rotate` and `transform-origin` strings, numeric tuples, font weights, discrete strings and booleans) and the `output` and `outputType` options are implemented as one numeric core over vectors: each output range is resolved into a plan (one vector per keyframe and a formatter back to the output type), and posterize, wrap, extrapolation, easing, `perceptual-scale` and tails run per component. Numeric ranges go through the same path with one-component vectors, keeping the arithmetic that made the numeric fixtures bit-identical. The CSS parser lives in `interpolate-css.ts`.

The docs name the forms but not the edge rules (when a string counts as a CSS value, defaults of missing components, how a rotation without an axis meets one with an axis, number formatting, error order, what an easing with `remotionShouldExtendRight` adds). Each rule was found by testing hypotheses against the recordings and is listed in `packages/core/COMPAT.md`; the oracle grid (38,266 values, 133 validation cases) is what keeps them honest. The rotation-axis rule in particular fits all 12 recorded multi-keyframe cases but is a fitted rule, not a derived one: a new recording that contradicts it means changing the rule. `Easing.in()` stays the identity: Remotion accepts `Easing.in(Easing.step1)` where only `Easing.step1` itself is allowed.

## D-037 Codecs and formats: the codec table, recipes and alpha bounds (2026-11-23)

`renderMedia` encodes every documented video `codec` but `av1`, through one table (`packages/renderer/src/codecs.ts`):

| Codec | Encoder, container | CRF (Remotion's table) | Pixel formats, default first | Audio codecs, default first |
|---|---|---|---|---|
| `h264`, `h264-mkv`, `h264-ts` | libx264; MP4, Matroska, MPEG-TS | 1 to 51, 18 | `yuv420p`, 4:2:2, 4:4:4, 10-bit | MP4 and TS: aac, mp3; MKV: aac, mp3, opus, pcm-16 |
| `h265` | libx265, MP4 tagged `hvc1` | 0 to 51, 23 | as H.264 | aac, mp3 |
| `vp8` | libvpx, WebM | 4 to 63, 9 | `yuv420p`, `yuva420p` | opus |
| `vp9` | libvpx-vp9, WebM | 0 to 63, 28 | `yuv420p`, `yuva420p`, 4:2:2, 4:4:4, 10-bit | opus |
| `prores` | prores_ks (`-vendor apl0`), MOV | none (rejected) | `yuv422p10le`; `yuv444p10le` for 4444 profiles; `yuva444p10le` with 4444 or 4444-xq | pcm-16 (documented), aac |
| `gif` | palette, GIF | none (rejected) | RGB(A) | none |

Choices beyond the docs:

- **Audio per container.** Remotion's compatibility table does not render in its docs (D-030), so each container lists what FFmpeg muxes into it; WebM takes only Opus, whose encoder runs at 48, 24, 16, 12 or 8 kHz (other `sampleRate` values fail early). A GIF renders no audio: `audioCodec`, `enforceAudioTrack` and `separateAudioTo` fail with it.
- **VP8 runs in constrained quality** with a 1000M bitrate cap: libvpx's VP8 encoder ignores the CRF with `-b:v 0` (CRF 4 and 9 both gave the same 68 kB file at 37.8 dB on a 2 s test signal; with the cap, CRF 9 gives 52.6 dB).
- **VP9 CRF 0 is lossless** (`-lossless 1`): Remotion's table calls 0 the best quality, and libvpx's CRF 0 alone is not lossless. Alpha needs `-auto-alt-ref 0` (D-019) for VP8 as well.
- **ProRes** defaults to `hq` or the composition's `defaultProResProfile`; `proResProfile` and `proResBitsPerMacroblock` with another codec fail, as do a CRF and alpha with a 4:2:2 profile. FFmpeg's decoder reports 4444 streams as 12-bit, and FFmpeg 7 writes no range into the MOV colour atom (ProRes is limited range by definition).
- **Alpha** needs `imageFormat: "png"` and an alpha pixel format; anything else fails before rendering.
- **GIF** is encoded in three FFmpeg runs: the captured images are copied to an intermediate file, the D-020 palette is built from all of it, then every frame is mapped to it, so long GIFs never hold their frames in memory. PNG capture keeps transparency. `numberOfGifLoops` follows D-020 and is ignored by other codecs.
- **Image sequences** are a CLI output, as Remotion documents (`--sequence`, `setImageSequence()`, a `--frames` list of single frames, `--image-sequence-pattern`, JPEG by default) into a folder, by default `out/<name>`: `renderMedia`'s output must be a file. The JSON result has `codec: null` and `sequence: true`.
- **`av1`** fails with `E_UNSUPPORTED_CODEC`: common FFmpeg builds (Homebrew's) carry no AV1 encoder, and Remotion itself does not offer AV1 on Linux arm64. (Wrong about Homebrew; AV1 is encoded since D-064.)
- **Matroska and AAC.** The AAC priming makes the audio of an MKV start at -21 ms; FFmpeg 7 decoding at a constant rate then duplicates the first video frame, so the tests decode frames as stored.

Measured in the pinned image and on macOS (same numbers): frame stamps decode exactly from every codec (60 frames each, GIF every 3rd frame at 10 fps), with the expected codec, pixel format, BT.709 tags, frame count and default audio codec. Alpha against the PNG frames of a fixture with an alpha ramp, a moving half-transparent box and an opaque frame stamp: ProRes 4444 and 4444 XQ and lossless VP9 within 1 code value in alpha and 0 in opaque colour; VP8 at its default CRF within 2. 4:2:0 chroma subsampling mixes the colour of transparent neighbours into opaque pixels next to them (up to 50 code values at the end of the red ramp), so opaque colour is compared at least 2 px from transparency. Lossy VP9 stays within D-019's bounds on the ramp (2 at CRF 4 and 20, 3 at 31), but the moving box's hard alpha edges ring more than D-019's static signal showed (3, 16, 16; 18 at the default CRF 28). The M5 alpha criterion therefore applies D-019's bounds to smooth alpha, and the tests bound the whole frame at the measured values plus headroom (4, 18, 20).

## D-039 Chunked rendering: renderChunk, a local worker and renderDistributed (2026-11-23)

The renderer gains two Motio functions, `renderChunk()` (a frame range to a video-only chunk with the encoder settings of a full render, each chunk its own encode starting on a keyframe) and `renderAudio()` (the audio pass and mixer of `renderMedia` over a frame range, written as a 32-bit float WAV), plus `planChunkedRender()`, which validates a chunked render exactly as `renderMedia` would before any chunk starts. `@motiojs/distributed` adds `LocalChunkWorker` (one Node child process per chunk running `renderChunk`; a cancel asks the child to close its browsers and FFmpeg and kills it after 10 s) and `renderDistributed({ serveUrl, composition, codec, outputLocation, framesPerChunk | chunks, concurrency, concurrencyPerChunk, worker, ... })`: plan, render chunks in parallel while the audio renders once, assemble with `assembleChunks`. Choices beyond the docs:

- **Chunk containers.** MPEG-TS for H.264 and H.265 (D-018), WebM for VP8 and VP9, MOV for ProRes, which reorder no frames. GIF (one palette for the clip), audio-only codecs and `everyNthFrame` are rejected for chunked renders, and `frameRange` must be one range.
- **Audio is encoded during assembly.** The audio rendered once is kept as float samples and encoded by AAC (or the container's codec) in the same FFmpeg run that concatenates the chunks, as `renderMedia` encodes the same samples while muxing, so the priming stays compensated and the bitstream is the same. An `hvc1` tag is reapplied for H.265 in MP4.
- **Workers.** `ChunkJob` is plain JSON (the resolved composition, the chunk, an output location and the data options of `renderChunk`), so a remote adapter (Lambda, Cloud Run, Kubernetes) implements `ChunkWorker.renderChunk` by running `renderChunk` where the bundle is reachable and making `job.output` available to the orchestrator; none is implemented, because testing one needs cloud spending. `concurrency` counts chunks rendering at once (default half the CPU threads, at most 8), `concurrencyPerChunk` the pages of each (default 1, as Remotion's `concurrencyPerLambda`).
- **CLI.** Remotion's CLI has no local chunked rendering, so `motio render --chunks=<n>` or `--frames-per-chunk=<n>` (with `--concurrency` counting chunks and `--concurrency-per-chunk`) is a Motio flag.
- **What "equal to the single-node render" can mean.** A lossy inter-frame encoder decides frame types and bits per GOP, so H.264 chunks are not bit-identical in decoded pixels to one encode of the whole range. Decoded frame hashes are compared where the codec's output does not depend on GOP placement: ProRes (intra-only) and lossless VP9, including their alpha variants and frames extracted from a media file; H.264 is held to exact frame stamps and a PSNR floor.

Measured in the pinned image (BeginFrame capture) and on macOS: 240 frame-stamped frames in 7 H.264 chunks of 37 decode to frames 0 to 239 once each, in order, with BT.709 tags, worst PSNR 44.1 dB against the single-node encode; ProRes and lossless VP9 chunked renders (also ProRes 4444 and VP9 with alpha, and an `OffthreadVideo` composition) have decoded frame hashes identical to the single-node render; the audio of three `fixtures/media` compositions (offset and trim, volume ramp, `playbackRate` 2) rendered in three chunks equals the single-node render sample for sample after decoding.

## D-040 Encoder input: no probe of the image pipe, JPEG colour converted in YUV (2026-11-23)

Profiling the full pipeline (timestamps around page open, seek, capture, encoder writes and the encoder's exit; 1080p, 60 frames, Apple M5) showed FFmpeg finishing about 600 ms after the last capture at every concurrency: by default FFmpeg reads up to 5 MB of an input to find its stream parameters before decoding, so on a short render it encoded nothing until stdin closed. The image pipe is now read with `-probesize 32 -analyzeduration 0` (codec and frame rate are given, the size comes from the first image): decoded frames identical, tail about 295 ms. Remotion's FFmpeg command line, observed while it renders, avoids the same delay with `-nofind_stream_info` on its own input format.

The exact JPEG path (Chrome's full-range BT.601 YCbCr to 16-bit RGB to BT.709 YUV, `accurate_rnd+full_chroma_int`) resampled the chroma twice and halved x264's speed. Measured on the captured frames of both benchmark compositions (x264 `medium`, CRF 18, PSNR against the captured frames decoded to RGB):

| Path | Encode, motion / timeline | Size, motion / timeline | PSNR, motion / timeline |
|---|---|---|---|
| Exact via 16-bit RGB (before) | 105 / 176 fps | 436 / 238 kB | 47.2 / 46.7 dB |
| Range only, BT.601 kept and tagged (D-032 candidate) | 231 / 396 fps | 401 / 199 kB | 46.0 / 47.9 dB |
| `colorspace` filter, BT.709 (chosen) | 225 / 385 fps | 312 / 200 kB | 48.2 / 46.9 dB |

The `colorspace` filter converts only matrix and range in YUV (`fast=1`: the pixels are sRGB, primaries and transfer are only tagged) and keeps the chroma samples Chrome encoded. It runs on frames first normalised to 8-bit planar YUV marked full range, because FFmpeg versions disagree on whether converting the decoder's `yuvj` formats also compresses the range (FFmpeg 8.1 still decodes JPEG to `yuvj420p`). The output stays BT.709, limited range, with the same tags, so the colour criterion and its test are unchanged; the palette round trip's worst error went from 1.97 to 1.00 code values with JPEG capture (1.00 with PNG, whose path is unchanged). D-032's range-only candidate is not needed: it is barely faster and would have changed the tags. Encoder settings otherwise stay: Remotion runs libx264 without `-preset` (its documented default `medium`) at CRF 18, as Motio does; fewer x264 threads lengthened the tail (`-threads 4`: 1005 against 611 ms), `-filter_threads` gained nothing, and stdin writes never waited more than 2 ms (mean under 0.1 ms), so the pipe and the reorder buffer need no change. Seek took 1 to 8 ms per frame and base64 decoding is negligible.

## D-041 Chrome draws unthrottled; opaque captures composite in software, transparent ones rasterise on the CPU (2026-11-23, closes D-031 and D-038)

`Page.captureScreenshot` took 49 ms per 1080p frame on one page whatever the format (D-006): Chrome draws at most one frame per display refresh and the screenshot waited for the next frames. `--disable-frame-rate-limit` draws a frame as soon as the capture asks for one: one page captures about 100 fps instead of 20. With software GL, GPU compositing made SwiftShader composite every frame on the CPU and pages competed for it (capture time at 8 pages rose from 49 to 145 ms on average). Measured raster and compositing variants, on capture speed and against Remotion's reference stills:

- Software compositing (`--disable-gpu-compositing`): fastest (8 pages about 330 fps of raw capture); every `fixtures/compositions` golden and template still identical to Remotion's render (PSNR infinite, was 46 to 73 dB), including the D-031 transparent edges; but the 3D `flip` transition over a transparent background misses the 40 dB floor (35.5 and 33.8 dB, SSIM 0.989): its antialiased edges lose alpha values of 1 to 6 that Remotion's carry.
- CPU raster with GPU compositing on SwiftShader (`--disable-gpu-rasterization`): every golden and template still identical, the flip frames at 44.1 and 45.7 dB, the D-031 edges identical: this is what Remotion's browser does. Capture is slow, 37 to 62 fps at 1 to 8 pages.
- GPU raster and compositing (the previous default): neither identical nor fast (17 fps on one page, 52 to 63 at 4 to 8).

So the compositing follows the capture: opaque captures (JPEG, the video default) composite in software, transparent ones (PNG with alpha, where edge alpha is visible in the output) rasterise on the CPU and composite on SwiftShader (37 fps on one page, against 17 before). Both draw 2D content identically; on opaque 3D-transformed layers the two differ only at antialiased edges (the flip frames at 41.1 and 38.2 dB, SSIM 0.9987 and 0.9977, every other transition frame identical). That difference is accepted for speed: the Remotion-exact compositing for opaque frames could not meet the performance criterion, and stays one option away (`chromiumOptions.flags: { "disable-gpu-compositing": false, "disable-gpu-rasterization": true }`). Hardware GL keeps Chrome's own choice. WebGL still runs on SwiftShader with software compositing.

Faster captures exposed a race the 49 ms had hidden: a CSS background image is requested only when style and layout run, and `check determinism` caught the first frames of a page without the CLI fixture's background. Before every screenshot the page now reads its layout and waits for the images, fonts and style sheets that requested, the loop BeginFrame pages already ran (D-033). The D-031 known mismatches are removed from `fixtures/templates/templates.json`: every template still is identical to Remotion's.

## D-042 Browser pool: pages spread over two browsers (2026-11-23, revisits D-007)

A session keeps a pool of browsers: pages with the same launch settings share one up to `pagesPerBrowser`, a recycled page is a new tab on the same browser, a crashed browser leaves the pool and its pages' frames are retried on a new one, and the session kills every browser when it closes (still before a render returns, including a cancelled one). With unthrottled frames and software compositing, raw capture (seek plus screenshot on the real bundle, 1080p, 10 CPU threads) scales with the layout: at 8 pages, 4 browsers of 2 reach about 330 fps, 2 of 4 about 250, 8 of 1 about 165 and 1 of 8 about 153 (one browser draws its pages' frames through one compositor). End to end, with x264 encoding on the same CPU, fewer browsers win, because each browser process takes CPU the encoder needs: two browsers render fastest at every concurrency tried (2: 2x1 0.74 s against 0.81 s for 1x2; 4: 2x2 0.68 s against 0.75 s for 4x1 and 0.79 s for 1x4; 6: 2x3 0.72 s; 8: 2x4 0.73 s against 0.83 s for 4x2 and 1.09 s for 8x1; motion composition). Default: the pages are spread over two browsers, and browsers of four pages are added above concurrency 8. `pagesPerBrowser` (a Motio option, `--pages-per-browser`, passed to chunk workers) chooses another layout; 1 restores D-007's isolation of one process per page. D-007's measurement (separate processes scaling better) held for GPU compositing through SwiftShader, which made pages of one browser compete for one compositor on the CPU.

## D-058 HTML-in-canvas presentations: Remotion's canvas lifecycle, gl-transitions shaders wired per presentation, two shaders rebuilt black-box (2026-11-23)

D-057 found HTML-in-canvas in the pinned Chrome, so `makeHtmlInCanvasPresentation()` and the twelve built-in canvas presentations are implemented instead of throwing. How Remotion drives a shader is not documented beyond the `draw()` arguments; it was read from probe compositions rendered by the published package (a custom shader that logs its calls and the markup, `--gl=swangle`):

- Every scene next to a canvas transition is wrapped on every frame, not only while the transition plays (CSS presentations are too, at progress 0 or 1), so the scene never remounts: an absolute fill holding a `<canvas content="drawable">` (`visibility: hidden`) around a `drawable` div (`visibility: visible`) with the scene, then an output canvas (`pointer-events: none`) of the composition's size times the device pixel ratio. The scene is rasterised with `drawElementImage()` in the canvas's `paint` event into an `OffscreenCanvas`; the shader draws on its own `OffscreenCanvas` (1 by 1 until sized), copied with `drawImage()` to the output canvas.
- While a transition between two scenes plays, the entering scene's canvas runs its shader on both images (`prevImage` the entering scene, `nextImage` the exiting one, `time` the timing's progress) and the exiting scene's canvas is cleared. Otherwise a scene is drawn alone with `time` 0 (as `prevImage` after its transition, `nextImage` before), which a shader turns into the matching end. A scene between two canvas transitions has one canvas, using its entering transition's shader. Transitions before the first scene or after the last change nothing. The canvas sits inside the CSS presentations of the scene's other transition. `presentationDurationInFrames` and `pixelRatio` are passed on every draw.
- Motio does the same in `<TransitionSeries>` (`HtmlInCanvasScene`): each frame holds a readiness handle from the commit until the scene is captured and drawn; the exiting scene hands its image to the entering one through a per-series registry keyed by transition and stamped with the frame. Without the API (other browsers, jsdom) the scenes are shown as cuts, with a warning. A canvas inside a `display: none` premounted sequence gets no `paint` event and does not hold the frame. `effects` other than an empty array throw `HtmlInCanvasEffectsUnsupportedError` (no effect pipeline, D-057).

Ten presentations credit a gl-transitions shader (MIT); they are ported with their licence header and a `NOTICE` entry. Remotion wires them differently from what its own porting guide says, and per presentation, so each was measured: `getFromColor()` reads the exiting scene with `progress = time` (crosswarp, dissolve, zoomInOut, linearBlur, ripple, bookFlip) or the entering scene with `progress = 1 - time` (crossZoom, dreamyZoom, filmBurn, swap), with `uv` top to bottom except swap, bottom to top. Versions: gl-transitions 1.43 for dreamyZoom (the flash lifts alpha too) and swap (opaque black floor), 2.x for the rest; linearBlur takes 20 by 20 samples (documented); swap's reflection is weighted by `reflection * y` of the projected point, growing away from the edge, measured; bookFlip's other directions turn the coordinates of the right-hand page turn.

`zoomBlur()` and `blurSlide()` credit no shader and were rebuilt from probes (coordinate gradients, flat colours, one-pixel dots, fitted on a CPU model): zoomBlur turns each scene by `rotation` times its share of the transition (the exiting scene clockwise on screen, the entering one counterclockwise), scales it by `cos a + max(w/h, h/w) sin a` so the turned frame covers the canvas, blurs it toward the center over 16 samples at `1 - 0.35 * share * i / 15` of the radius, and crossfades linearly. blurSlide moves both scenes, repeated past their edges, by one frame with `d = smootherstep(time)` (from-left moves the content left, measured), blurs along the slide with a centered box of `2 * blur * min(d, 1 - d)` frames in two passes (32 spaced samples into an 8-bit framebuffer, 32 more filling each gap), and crossfades with `smoothstep(0.3, 0.7, d)`.

`fixtures/transitions-canvas` (166 stills: every presentation, their options, a custom documented shader, scene chains, mixed CSS and canvas transitions, transitions at the ends): nine presentations, the custom shader, the chain and the ends identical on every frame; the rest at least 50.4 dB (blurSlide at its midpoint), 66 dB elsewhere. `scale: 2` and premounted scenes are identical too. Not done: `motionBlur` on transitions (still warns and draws without it) and `effects`.

## D-064 AV1 output with SVT-AV1, libaom as the fallback (2026-11-23, corrects D-037)

D-037 left `av1` out because "common FFmpeg builds (Homebrew's) carry no AV1 encoder". That was wrong: Homebrew's FFmpeg 8.1.2 has `libsvtav1` (SVT-AV1 4.2.0), and Debian trixie's 7.1.5 (the pinned image) has `libsvtav1`, `libaom-av1` and `librav1e`, with `libdav1d` to decode. `av1` now goes through the codec table like every other codec:

| Codec | Encoders, in order | Container | CRF (Remotion's table) | Pixel formats | Audio codecs |
|---|---|---|---|---|---|
| `av1` | libsvtav1, else libaom-av1 | MP4 | 0 to 63, 30 | `yuv420p`, `yuv420p10le` | aac, mp3 |

- **Encoder choice.** A codec now lists its encoders in order of preference (`encoders` in the table); a render probes FFmpeg once and, when it has none of them, fails before any page opens with `E_FFMPEG_ENCODER_MISSING` naming both (`libsvtav1 or libaom-av1`). For AV1 the order also depends on SVT-AV1's version, read from the line it prints when FFmpeg encodes one 64x64 frame (cached per executable): SVT-AV1 3.0 or later first, then libaom, then an older SVT-AV1. The reason is measured in the pinned image, whose SVT-AV1 is 2.3.0: it replaced a whole 16 px block of the frame-stamp fixture with the grey around it (mean luma 128) on some frames, at the default CRF and at CRFs from 20 to 50, at presets 6 and 10 and with temporal filtering on or off, while 4.2.0 on macOS decoded exactly at every CRF from 10 to 63 and every preset from 4 to 10. SVT-AV1 2.3 also has no lossless mode (`lossless=1` is rejected and FFmpeg carries on at CRF 35), so with an old SVT-AV1 and no libaom, CRF 0 fails with `E_FFMPEG_ENCODER_MISSING` instead of silently encoding lossy. SVT-AV1 is preferred when recent: BSD licence with the AOM patent grant, and faster (30 1080p frames: 0.7 s for SVT-AV1 2.3 at its default preset, 2.5 s for libaom). libaom runs at `-cpu-used 6 -row-mt 1`, because its default speed (1) takes seconds per 1080p frame. `doctor` lists the encoder each codec would use and warns about codecs with none.
- **CRF 0 is lossless**, as for VP9 (D-037). SVT-AV1 reads a CRF of 0 as "not set" and falls back to its own default (35; measured: CRF 0 gave 41.7 dB on `testsrc2`, CRF 1 62.4 dB), so CRF 0 passes `-svtav1-params lossless=1` (infinite PSNR on 4.2.0). libaom's CRF 0 with `-b:v 0` is lossless as it is; its `-lossless 1` option, through FFmpeg 7.1, gave 46.1 dB and is not used.
- **Pixel formats.** The two encoders share 8- and 10-bit 4:2:0 (SVT-AV1 takes nothing else), so the table offers those; there is no alpha in either encoder, and Remotion's docs mention none for AV1.
- **Container and audio.** Remotion's docs give `.mp4`, `.webm` or `.mkv` for AV1 and the CLI's default extension is `.mp4`; Motio's container follows the codec, so `av1` writes MP4 with the audio MP4 carries elsewhere in the table (aac by default, mp3). `x264Preset` does not apply, as documented.
- **Colour.** The same filter and tags as every YUV codec (BT.709, limited range): SVT-AV1 takes its colour metadata from the frames, so the `setparams` tagging of D-040 is what writes primaries and transfer (without it they came out `unknown`).
- **Chunks** are WebM, like VP8 and VP9: AV1 has no reordered frames at the container level. Every worker of a chunked AV1 render must have the same encoder, or the chunks' sequence headers differ.
- SVT-AV1 prints its configuration to stderr at its default log level, which would bury FFmpeg's error in a failure message; encodes run with `SVT_LOG=2` (warnings and errors) unless the variable is set.

Remotion notes that its own builds offer no AV1 on Linux arm64 or Lambda; Motio has no such gap because it uses whatever FFmpeg it is given (and `@motiojs/ffmpeg`, D-065, has SVT-AV1 on every platform).

Measured on macOS (FFmpeg 8.1.2, SVT-AV1 4.2.0) and in the pinned image (FFmpeg 7.1.5, SVT-AV1 2.3.0, so libaom 3.12.1 encodes): frame stamps decode exactly from all 60 frames at the default CRF with PNG capture, at `yuv420p10le` with JPEG capture, and losslessly at CRF 0; ffprobe reports `av1`, the pixel format, BT.709 primaries, transfer and matrix, `tv` range and 60 frames; a lossless chunked render (4 chunks) decodes to the same frame hashes as the single-node render; libaom alone (SVT-AV1 hidden from FFmpeg's encoder list) gives exact stamps; FFmpeg with neither encoder fails before rendering; `motio render --codec=av1` writes a tagged AV1 MP4.

## D-065 `@motiojs/ffmpeg`: an optional pinned FFmpeg, GPL binaries published with their sources (2026-11-23, supersedes the "no binary" part of D-002)

D-002 kept FFmpeg a system dependency and named the way out: "a pinned download can be added as an opt-in package". The author chose that option. `@motiojs/ffmpeg` is an optional package whose JavaScript (Apache-2.0) downloads a pinned FFmpeg 8.1.3 and ffprobe for the current platform on first use and checks them; the system FFmpeg stays the default when the package is not installed.

- **Download and verification.** No install script: nothing runs during `pnpm install`. On first use (a render, `motio ffmpeg ensure`, or `ensureFfmpeg()`), the archive `ffmpeg-<version>-<build>-<platform>.tar.gz` is fetched from the GitHub Release `ffmpeg-<version>-<build>` (or `MOTIO_FFMPEG_BASE_URL`, for mirrors and tests), its size and SHA-256 are checked against the manifest committed in the package (a larger body is cut off as soon as it exceeds the size), it is unpacked by the package's own tar reader (files and folders only, no links, no path outside the target) into a private temporary folder, and both binaries are run: the version must be the pinned one and every required encoder must be listed. Only then is the folder renamed into `~/.cache/motio/ffmpeg/<version>-<build>/<platform>` (or `MOTIO_FFMPEG_CACHE`), with a completion marker written last; a race between processes ends with one rename winning and the others using its folder, and a leftover folder without the marker is replaced. Errors: `E_FFMPEG_UNSUPPORTED_PLATFORM`, `E_FFMPEG_DOWNLOAD`, `E_FFMPEG_DIGEST`, `E_FFMPEG_VERIFY`. Until the release exists, the default URL is refused before any request (the owner in the URL is a placeholder, `RELEASE_OWNER`).
- **Resolution order**, in the renderer, the CLI and the assembly of chunked renders: `ffmpegExecutable`/`ffprobeExecutable` (Remotion's `binariesDirectory` for `stitchFramesToVideo`), then `MOTIO_FFMPEG`/`MOTIO_FFPROBE`, then `@motiojs/ffmpeg` when installed, then `PATH`. The package is never a dependency of the renderer; it is found by walking up the `node_modules` folders from the renderer and from the working directory, not through Node's resolver, because `pnpm exec` sets `NODE_PATH` to the store's hoisted folder, where every package of a workspace is visible (this workspace included) whether the project depends on it or not. `doctor` names the source and never downloads (a package whose build is not downloaded yet is a warning that points to `motio ffmpeg ensure`); `motio render --json` records the path, version and source of the FFmpeg that encoded the video, and passes the resolved binaries to the renderer, so chunks and the result name the same build.
- **What is in the build.** FFmpeg 8.1.3 (signature checked against FFmpeg's release key), x264 (stable, pinned commit), x265 4.2 (8- and 10-bit in one library, because `h265` with 10-bit pixel formats is a Motio codec), SVT-AV1 4.2.0, libvpx 1.17.0, dav1d 1.5.5 (AV1 decoding), Opus 1.6.1, LAME 3.100, Mbed TLS 3.6.8 (HTTPS input: remote media is read by FFmpeg itself), and on Linux zlib 1.4; FFmpeg is configured with `--disable-autodetect`, so nothing from the build machine leaks in. Linux builds are fully static (Alpine, musl, image pinned by digest) and run on any distribution of the architecture; macOS builds link only system libraries and frameworks and run on macOS 12 or later.
- **Licensing.** x264 and x265 make the binaries GPL; Mbed TLS (Apache-2.0 or GPL-2.0-or-later) is accepted by FFmpeg's configure only with `--enable-version3`, so the binaries are **GPL-3.0-or-later**. No non-free component (`libfdk_aac` stays out; AAC is FFmpeg's own encoder). Motio is not affected: it runs FFmpeg as a separate program and the package contains no binary, only the code that downloads one, so the Apache-2.0 licence of Motio, of users' projects and of their videos is unchanged. GPL distribution duties fall on whoever distributes the binaries, here the project's releases: each release publishes, next to the archives and `SHA256SUMS`, the exact source tarball of every component (git sources as `git archive` of the pinned commit), their digests, the build scripts at the building commit, and the licence texts; every archive also carries `LICENSE.md`, `licenses/` and `BUILDINFO.json` (sources with digests, configure flags, compiler). That is the "corresponding source" offered alongside the object code (GPLv3 section 6(a)/(d)). musl and libgcc are linked into the Linux binaries: musl is MIT and shipped as source too; libgcc is covered by the GCC Runtime Library Exception.
- **Builds.** `tools/ffmpeg-build/` holds the pinned `sources.lock`, `fetch-sources.sh` (verifies every tarball and commit), `build.sh` (macOS natively or cross-compiled to x86_64 from Apple Silicon, and Linux inside the pinned image via `build-linux.sh`), `package.sh`, `update-manifest.mjs` (writes the digests of the archives to publish into the manifest) and `.github/workflows/ffmpeg-build.yml` (builds every platform on GitHub's runners and creates a draft release with everything above). The build checks encoders, decoders, HTTPS and linkage and encodes a one-second smoke test with every encoder; `release-archive.integration.test.ts` installs the local archive of the current platform through a local HTTP server and renders AV1, 10-bit H.265 and VP9 with it, with exact frame stamps and BT.709 tags.
- Archives are not byte-reproducible across machines (compiler versions, timestamps in static libraries), so the manifest must carry the digests of the archives actually published: whichever set is published, `update-manifest.mjs` is run on it.

Left for the author, in order: (1) create the GitHub repository; (2) set `RELEASE_OWNER` in `packages/ffmpeg/src/manifest.ts` to its owner; (3) run the `ffmpeg-build` workflow with `release` checked, or publish the locally built archives with the same set of files by hand; (4) run `update-manifest.mjs` on the published archives and commit the manifest (the digests committed now are those of the local builds); (5) publish the draft release, then `@motiojs/ffmpeg`. A short legal review of the GPL distribution setup (the GPLv3 build, the source offer through the release, the Mbed TLS licence choice) is advisable before step 5. The three components beyond the original plan (x265, Mbed TLS with the GPL-3.0 build it implies, dav1d) were confirmed by the author on 2026-11-23. Revisit: Windows builds (not attempted); byte-reproducible archives, which would let anyone check a published archive against a rebuild.

## D-066 Motio stops chasing parity: compatibility is a layer, not the goal (2026-11-23)

Until now work was chosen by the gap with Remotion: which symbols, packages and behaviours it has that Motio lacks. That criterion has done its job (M1 to M3, every official template, the Tier 2 and most Tier 3 packages) and now produces diminishing returns: what is left (`@remotion/effects`, Skia, the web renderer, media-parser, webcodecs, whisper-web, the cloud adapters) is large, recent or a separate product, and would make Motio a follower of someone else's roadmap. The goal from here is a complete, working tool in its own right; Remotion compatibility stays as an entry point.

- **Compatibility follows Remotion on a schedule, not release by release.** The target is pinned (4.0.545 today); the alias, the symbol manifest and the oracle tests keep guarding against regressions. At most every few months, or at a significant Remotion minor release, the oracle pin is moved and every fixture re-recorded through its record command: a changed behaviour of an API Motio already supports is always aligned, because that is where user projects break; a new symbol or package is added only when it is in real use or someone asks for it, never to close the manifest. Each update is one decision entry with the old and new pin and what changed. A major release (Remotion 5.0 is announced, with a new licence) is assessed on its own.
- **Recording the oracle requires the right to run Remotion.** Remotion's licence is free for individuals and for organizations of up to 3 people; larger organizations need a company licence. Whoever runs a record command must be eligible (the author records as an individual for this personal project, D-009) or licensed, and the terms in force are checked again before each scheduled update, since they bind what the oracle may do. Remotion is only observed from outside through its public API: its source, type declarations and source maps are never read, and the published code is never decompiled or modified. remotion.dev content belongs to Remotion: Motio's documentation and examples are written from Motio's code, never copied or closely paraphrased from it.
- **Work is chosen by what someone needs to use Motio without knowing Remotion**: scaffolding (`motio init` with Motio's own starters), user documentation written for Motio (`docs/guide/`), errors and `doctor` that say how to fix, and the pieces real pipelines need (preloading for the Player, animated images, media functions in the Node API, a browser reused across renders, a general text background).
- **Where Motio can do better, it designs its own API** and, when useful, maps Remotion's on top through the alias. First case: `@motiojs/text` with a configurable `<TextBackground>`, of which `@remotion/rounded-text-box` is one preset. Candidates to design with the author one at a time: visual regression tests for videos, incremental re-rendering, an effect system of Motio's own instead of `@remotion/effects`.
- **Dropped from the plan**: `@remotion/effects` (D-057, D-060 stay as the record), Skia (D-063), web-renderer, media-parser, webcodecs, whisper-web, `<ThreeWebGPUCanvas>`, `HtmlInCanvas` and the minor core symbols. The Lambda and Cloud Run adapters wait for a use case and approved spending.

Revisit if users arrive mainly as Remotion migrants blocked by missing symbols: then parity work returns, driven by their reports; or if Remotion's terms forbid using it to build an alternative, which would end the scheduled updates (the recorded fixtures stay). Compatibility is a means, not a constraint: if keeping it stops paying off (a Remotion release that diverges, terms that forbid the oracle, a design Motio needs that the alias would block), it can be frozen or dropped, and Motio must stand and evolve on its own regardless (author, 2026-11-24).

## D-072 Every captured frame is rasterised as on a fresh page (2026-11-23)

Found while building the `basic` starter: an element whose `transform` changes from frame to frame was drawn differently depending on the frame the same tab rendered before (up to 222 levels out of 255 with `will-change`), so `motio check determinism` failed on it. Cause, confirmed in Chromium's source (BSD, outside the clean room, which covers only Remotion): Blink's raster invalidation skips an element whose translation changes by less than 0.01 px or whose other transform components change by less than 1e-4, and keeps the last transform it painted as the reference, so the pixels depend on which frame set it; with `will-change: transform` Chrome keeps the raster scale of the first frame painted. Evidence: the wrong bytes equal the previous frame's, stop at 256 px tile edges, and appear exactly on the frames where a settling spring moves by less than 1e-4. Remotion's configuration (GPU compositing, CPU raster) shows the same differences; `--disable-partial-raster` changes nothing.

Fix: before each capture, after the seek, the renderer hides the document (`opacity: 0` on the root element) until Chrome has drawn one hidden frame (`requestAnimationFrame` then `setTimeout`), then shows it again, so everything is rasterised again as on a new page. It runs in a CDP isolated world, so page code cannot replace `requestAnimationFrame` or see the change except through a `MutationObserver` on `<html>`. With BeginFrame the hidden frame is a full BeginFrame before the existing pre-frame. Variants measured at 640x360 against a fresh page per frame: one `requestAnimationFrame` leaves the errors (+17 ms per frame); two fix them (+0.5 ms); hiding before the seek fixes them but costs 28 ms per frame at 1080p against 12 to 14; resetting before the seek leaves 35 wrong frames; the chosen variant fixes them for +0.3 to 1.3 ms. Before and after: 59 differing PNG frames and 57 JPEG to 0 over ascending, descending and random orders at concurrency 1, 4 and 8; the original `basic` design (logo and caption animated with `transform`) from 20 differing frames of 120 to 0. `make bench --assert` still passes (Motio 1.85 / 1.35 / 1.43 s against Remotion 6.60 / 2.21 / 1.70 s); alternating runs with and without the reset differ by less than 2%. `transform-determinism.integration.test.ts` covers scale from 0, scale near 1, subpixel rotation and translation, steps below 1e-4 and `will-change`; all eight cases fail without the fix, on macOS and in the pinned Linux image.

Open: with BeginFrame at concurrency 4 some frames come out entirely wrong (up to every byte, 255 levels) whether the reset runs or not, a separate, older defect of the opt-in BeginFrame path (screenshots are the default, D-043). M1's determinism check compared runs with each other on a box that always moved above the tolerance, so it could not see this: two ascending runs are wrong the same way.

## D-075 BeginFrame waits until the page is on screen, and runs one page at a time (2026-11-23)

With BeginFrame at concurrency 4, some frames came out entirely transparent (the hidden state of the raster reset) or equal to the page's previous frame. Cause, from per-BeginFrame damage logs and Chromium's source (viz `DisplayScheduler`, `ExternalBeginFrameSourceMojo`): the screenshot copies the surface at the next display draw, and the display compositor draws without waiting for a renderer that did not get that BeginFrame in time or still has an undrawn frame, so the renderer's frame lands one BeginFrame late and the lag carries over. Extra evaluations between BeginFrames made it disappear, and the old code missed 1 frame in 540 even at concurrency 1 under load. Fix: in the isolated world a guarded `requestAnimationFrame` confirms that a main frame ran with the document hidden; after showing it, the renderer sends BeginFrames until a main frame committed and a later BeginFrame found nothing to draw, then takes the screenshot. Wrong frames: concurrency 4 from 2 to 5 of 60 to 0; concurrency 1 under stress from 1 of 540 to 0; concurrency 8 from 13 to 22 of 60 to 4 of 180. CDP exposes no "frame presented" signal that would rule out the rest, so BeginFrame above concurrency 1 now fails with `E_BEGIN_FRAME_UNSUPPORTED`, pointing to concurrency 1 or the screenshot path. At 1080p a BeginFrame page now takes 0.82 to 1.02 of the screenshot time (before 0.99 to 1.03); the test that asserted BeginFrame is faster already failed one round in two and is now a regression bound at 1.5 times. Residual risk: two chunk workers running in parallel, each at concurrency 1 with BeginFrame, recreate the condition without the renderer knowing. BeginFrame has not been faster than screenshots since D-043 and now costs up to 18% more: deprecating it is a candidate. Revisit if Chrome exposes a presentation signal through CDP.

## D-078 BeginFrame capture is deprecated (2026-11-24)

BeginFrame was the Linux default because it was 3.8 times faster than the screenshots of the time (D-013). ## D-082 Fixes for the issues the promotional project found (2026-11-24, closes the list in D-080)

- **`<Freeze>` follows Remotion.** The recorded oracle (37 scenes, `tools/oracle`, and a real `renderStill` probe) shows that Remotion maps the frozen frame onto the composition, through `from`, `trimBefore`, `playbackRate` and the current `<Loop>` iteration, clamps it to the composition's first and last frame and maps it back: in a `<Still>`, `<Freeze frame={90}>` shows frame 0, and nested sequences are visible. Motio does the same for `<Freeze>` and the `freeze` prop of `<Sequence>` and `Interactive`, since compatibility is at stake (D-066), and adds what Remotion lacks: a once-per-page warning naming the frame shown and how to get the one asked for (`<Freeze frame={0}><Sequence from={-90}>`). Motion blur components, which sample frames outside the composition without clamping in the recordings, use an internal `<HoldFrame>` that skips the clamp.
- **`motio/client` types** (to become `@motiojs/motio/client` with D-081) declare what Motio's bundle accepts (asset files, `?raw`, `?url`, CSS), written for Motio rather than referencing `vite/client`, since Motio does not depend on Vite in user types and uses `process.env`, not `import.meta.env`. Every starter, `promo/` and the guide examples use them; the init integration test type-checks these imports in each starter against the packed package.
- `motio init` realigns the comments in the generated README after filling the package manager's commands. The preview header shows a still as "1200×630 · still" and pluralises frames.
- **GIF progress** has three equal parts (capture, palette, encode); the intermediate file goes to FFmpeg on stdin so the palette pass reports the share read (FFmpeg reports nothing until the palette is written, and a second `-f null` output does not help), the encode pass reads `frame=` from `-progress`, and `encodedFrames` counts the final GIF's frames only.
- **Files outside the project in `motio dev`.** D-080's premise was partly wrong: JS and `?raw` imports from outside the project already worked outside a workspace; assets referenced only from CSS `url()` or `new URL(..., import.meta.url)` were refused with 403. Every file a transformed module references is now added to `server.fs.allow` (`fs.deny` still wins), so the dev server serves what the bundle includes; a refused file is a warning that names it and how to include it. Inside a workspace the whole root stays allowed, as before.

## D-083 Fixes from a new-user usability audit (2026-11-24)

An agent followed the guide as a newcomer, in a project outside the repository, and logged every friction point; four agents fixed them by area, each finding with a test.

- **Trying Motio before npm**: `make try DIR=... [TEMPLATE=...]` packs the published packages into `.motio/tarballs/` inside a new project and points every `@motiojs/*` at its tarball with relative paths, so the project can move (`make try-update` repacks after a pull); the guide and READMEs explain it, and the landing hides the copy button of `pnpm create motio` while `NPM_PUBLISHED` is false.
- **FFmpeg**: when `@motiojs/ffmpeg` cannot download its build (archives not published, unsupported platform, network) and an FFmpeg on `PATH` works, renders use it with `W_FFMPEG_FALLBACK`; a wrong digest or a failed verification still stops the render. `doctor` reports unpublished archives as a failure even while the fallback works, and the docs present the package as coming soon.
- **Errors say where**: page stacks are mapped through the bundle's source maps in Node; `MotioError.details` carries `frame`, `compositionId`, `source` (first frame in project code), `hint`, `option` and `rawStack`, and the CLI prints `at frame N of Composition, path:line:column`, with paths relative to the working directory so the terminal can open them. Missing assets and fonts are `E_ASSET_NOT_FOUND` and `E_FONT_LOAD` with the path in `public/` and the nearest name; `<Img>` fails at once on a 404 instead of retrying for 7 s (Motio's own behaviour, D-066); a font failing at module level fails the first frame instead of breaking `compositions`.
- **Warnings reach the user**: page warnings are returned by `renderMedia`, `renderStill` and `renderFrames` (`warnings: { code, message, frame? }[]`, deduplicated) and printed once by the CLI (`renderWarnings` in `--json`): fallback fonts, `W_MATH_RANDOM`, `W_STATIC_FILE_CASE`, `W_TIMELINE_SHORT` for a `TransitionSeries` that ends before the composition. `onDelayRenderPending` reports open handles every 5 s and the CLI prints a waiting line naming `--timeout`.
- **CLI**: the project root is the nearest `package.json` above the entry point (stopping at a working directory that has its own `public/`); mistyped flags and commands get the nearest valid one by edit distance; `--version`; every invalid-input code exits with 2; unknown extensions list the supported ones; the determinism report groups frames into ranges and names the likely cause (`diagnosis` in `--json`); `check flicker` also compares 16 px blocks against five times `--threshold`, so small jumping elements are caught; Chrome's first download shows progress everywhere; image sequences default to PNG named `frame-[frame].[ext]` (Remotion's CLI writes `element-*.jpeg`; the config still wins); messages no longer mention `remotion.config.ts` in Motio projects and `MOTIO_` variables reach the bundle like `REMOTION_` ones (tool settings such as `MOTIO_FFMPEG` excepted).
- **Preview**: a timeline with one row per sequence and its `name`, nested as in the code, scrubbable by mouse and keyboard, built on a sequence registry in core that only the preview provides (renders and the plain Player pay nothing); a Problems panel (failed loads, open `delayRender` handles with where they were called, cancellations with their code, page warnings); errors shown with mapped stacks, a code frame and React internals folded; warnings for props keys absent from `defaultProps` and the schema; `HH:MM:SS:FF` timecode; drawers below 1100 and 720 px; stills saved to `out/`; Motio's own build-error overlay instead of Vite's.
- **Player clock**: it waits until every playing media element has advanced for 60 ms (at most 1 s), starts from the slowest and realigns the others. Cause: with Bluetooth output (0.23 s `outputLatency` measured) audio started 350 to 540 ms after `play()` while the clock started at once, staying 0.22 s ahead for the whole playback, under the 0.45 s reseek threshold. The sync thresholds of the tests are unchanged.

The renderer now kills the browsers' process groups on exit and on SIGTERM, SIGINT and SIGHUP when the host does not listen for that signal, then re-raises it so exit codes stay 143, 130 and 129.
- **Docs**: READMEs for transitions, player, captions, zod-types, media and gif, type-checked like the guide; every guide snippet shows its imports; a Schema section; how to run a Node render script; how to compute a `TransitionSeries` duration; the `basic` starter shows its title at frame 0 and `captions` has a synthesised tone on every word.

Benchmark after the round, at low load: Motio takes 0.29, 0.60 and 0.86 of Remotion's time at concurrency 1, 4 and 8. Left: the `E_FFMPEG_NOT_FOUND` hint changes once the archives are published.

## D-085 `motio.config.ts`, Motio's own configuration file (2026-11-24, closes the open point of D-069)

`import { defineConfig } from "@motiojs/motio/config"`, a default export, found in the project root as `motio.config.ts`, `.mts`, `.js` or `.mjs` and compiled with Vite's module runner (no new dependency); `--config <path>` picks a file, read as a Remotion config when it is named `remotion.config.*`. Every key maps to an option the CLI or the Node API already reads, with the Node API's names, so `...config.render` works from code:

- project: `entryPoint`, `publicDir`, `outDir` (for `render`, `still` and `frames`), `envFile`, `logLevel`, `tailwind`, `vite(config)`;
- `render`: codec, quality, audio and image options, `everyNthFrame`, `imageSequencePattern`, `timeModel`; `still`: its own `imageFormat`, `jpegQuality`, `scale` and `overwrite`, so video at 1x and thumbnails at 2x coexist;
- `browser`: `executable`, `timeoutMs`, `captureMethod`, `pagesPerBrowser`, `chromiumOptions`; `ffmpeg`: `executable`, `ffprobeExecutable`; `dev`: `port`, `host`, `open`, `keyboardShortcuts`.
- Per-run options (composition, output, frames, props, size overrides) and niche ones stay flags.

Precedence: flag, then `MOTIO_*` variable, then file, then default. The variables are a closed list of machine settings named after their flag (`MOTIO_CONCURRENCY`, `MOTIO_TIMEOUT`, `MOTIO_LOG`, `MOTIO_GL`, `MOTIO_PAGES_PER_BROWSER`, `MOTIO_BROWSER_EXECUTABLE`, `MOTIO_CAPTURE_METHOD`, `MOTIO_FFMPEG`, `MOTIO_FFPROBE`), never passed into the bundle; project choices such as the codec have none. Validation reports every problem at once with the nearest key (across groups: `crf` at the top level suggests `render.crf`) and the nearest value, as `E_INVALID_CONFIG` with exit code 2. When both files exist, `motio.config.ts` wins and every command names the ignored `remotion.config.ts`. A port from the file moves to the next free one; only `--port` is strict. The Node API reads nothing implicitly: `loadConfig()` (from `@motiojs/bundler`) returns the config, the ignored file, and ready `bundleOptions` and `sessionOptions`. `motio init` writes a commented `motio.config.ts` in every starter and `doctor` names the file in use. Types and `defineConfig` live in `@motiojs/core/config` (no dependencies), re-exported by `@motiojs/motio/config`; the schema sits next to the loader in the bundler, kept aligned with the types by a compile-time constraint. Left: the commands read `render.timeModel` once the virtual clock's `--time-model` lands.

## D-086 The virtual time model is supported (2026-11-24, completes D-005)

`timeModel: "frame" | "virtual"` on `renderMedia`, `renderStill`, `renderFrames`, `renderChunk`, `renderAudio` and `renderDistributed`, `<Composition timeModel>` as a per-composition default (in `CompositionInfo` and `VideoConfig`), `--time-model` and `render.timeModel` in `motio.config.ts`. Precedence: flag, config, composition, then `frame`, which stays the default; listing compositions always uses the frame model. In the virtual model the page's `Date`, `performance.now`, timers, `requestAnimationFrame` and `Math.random` follow the video's time (main frame only, not iframes).

- Virtual time only moves forward, one frame at a time from 0, on every page: before rendering frame n a page replays every frame it has not rendered yet, with the seek's steps and no capture, in calls of at most 30 frames so each stays inside the watchdog; a frame at or before the last one rendered opens a fresh page; pages are not recycled by default. D-005's "warm up from the range start" was not enough: without the full warm-up 59 of 60 frames differed. The pool keeps the shared ascending queue rather than contiguous ranges per page, since far frames would otherwise wait in the reorder buffer. The fresh-page reference (D-074) is the model's own semantics: a page per frame starts from 0.
- Measured on a fixture with a timeline engine written for the test (GSAP's licence is not open source and restricts use), a canvas on `requestAnimationFrame`, a `setInterval` counter, `Date`-driven motion and `Math.random`: 0 of 60 frames differ from one ascending render with a fresh page per frame, descending and random orders at concurrency 1, 4 and 8, partial ranges, pages recycled every 7 frames, four ProRes chunks and `check determinism --reference fresh`; in the frame model 60 of 60 differ. Timers, CSS transitions, timer-based async and keyframes from the usability session also match. Cost at 1080p over 300 frames: 1.00 to 1.02 times the frame model at concurrency 1, 1.07 to 1.18 at 4 and 8; a warm-up step costs about 1 ms against 13 ms for a capture, a fresh page about 350 ms. The frame model's capture path is unchanged.
- Page warnings are deduplicated by code plus a stable key the page may give, so `W_MATH_RANDOM` appears once per render with the first frame in its `frame` field. `renderDistributed` lost an explicit `timeModel`; fixed. Old bundles without the model are refused through the page's `timeModels`, without a protocol version bump.

Open: Chrome's GPU-accelerated 2D canvas differs in 7 of 360 frames under heavy load (load 30 to 43) in both models, 0 with `--disable-accelerated-2d-canvas` (the tests draw canvases in software); CSS transitions are seeked like keyframe animations, from the start of the sequence rather than from the style change; in the frame model a real `requestAnimationFrame` loop without the frame rate limit keeps the settle loop busy (about 10 s per frame on the fixture); the preview and the Player run on the real clock, so clock-driven code does not follow scrubbing; the time zone is not fixed across machines; `check determinism` does not suggest `--time-model=virtual`. The canvas point is closed by D-089, the others by D-090.

## D-087 Transparent captures clear the tiles under sliding scenes (2026-11-24, extends D-072)

Reported by the author's sessions: `slide()` with `springTiming()` was not deterministic on its cuts (10 of 25 frames on Motio's own teaser), and `check determinism` blamed randomness. Only transparent PNG captures were affected (`check determinism`'s PNG, image sequences, videos with alpha); JPEG and opaque video were already deterministic. Cause, from the pixels and Chromium's source: each differing frame changes one column, the seam between the two scenes, in 256 px tile-high blocks; on a fresh page the seam's antialiased pixel is semi-transparent (alpha 194), on a reused page it is opaque and blended with an earlier frame (117 + 0.239 × 42 = 127). When two opaque drawings meet on a fractional edge, Blink counts them as covering the whole layer (`gfx::MaximumCoveredRect` in `PendingLayer`), marks the layer opaque, and `RasterSource::PlaybackToCanvas` then does not clear tiles before drawing, so the seam blends with whatever the reused tile memory holds. D-072's reset forces a new raster but not a clear.

Fix: for transparent captures only, during the capture the reset adds a 1 px semi-transparent square just below the viewport, outside the captured area, so the layer extends past the opaque drawings, is no longer opaque, and every tile is cleared; the square is removed after the capture. Lowering the root's opacity to 0.99999994 was deterministic too but wrote alpha 254 instead of 255 with composited (`will-change`) layers, so it was dropped. Measured: the `slide-seam` fixture from 11 to 24 differing frames of 60 per run to 0 in all seven runs; the teaser's cuts from 60 of 96 to 0 against `--reference fresh` at concurrency 4 and 8; fresh pages give the same pixels with and without the fix on 213 frames; `make bench --assert` still passes (it captures JPEG, where the fix does nothing). `slide-seam` joins D-074's suite in PNG.

`check determinism` now measures, for each differing frame, how many pixels change and where (`differingPixels`, `region` in `--json`); when every differing frame changes at most four rows or columns, the cause is `raster`, worded as a probability, with the run pattern kept beside it, and `random` also says "probably". No agent-facing rule about moving whole scenes is needed. Note for transparent output: the seam between two opaque sliding scenes stays a slightly transparent column even on a fresh page (antialiasing); a background on the composition's root hides it.

## D-089 `raster` and `canvas`: the CPU raster and software canvases by default, the GPU raster when the project asks for `gl: "swangle"` (2026-11-25, extends D-041, closes the raster point of D-088)

Two findings had one cause in common, how Chrome draws: Chrome's GPU-accelerated 2D canvas differed under heavy load (D-086), and the M4 references differed from Motio at the antialiased edges of thin strokes, text and borders (D-088). Every combination of raster (CPU, GPU) and canvas (software, GPU) was measured on macOS against the fresh-page reference (D-074), Remotion's recorded references and the benchmark; the measurement left the defaults to the author, who chose them.

- **Remotion's pixels depend on its `gl`.** The M1 stills recorded with Remotion's default `gl` are identical to Motio's CPU raster (29 of 29) and not to the GPU raster (1 of 29); the same stills recorded with `gl: "swangle"` (a throwaway checkout, never committed) are identical to the GPU raster (29 of 29) and not to the CPU raster (1 of 29). The M4 references are recorded with `swangle`: with the GPU raster 184 of 186 compositions are within the thresholds (148 identical) against 161 (13 identical) with the CPU raster, with no regression. On references recorded with the default `gl` the GPU raster is worse: 3 template stills (OnlyLogo 33.3 dB, Logo 35.9 dB, Overlay 37.7 dB, D-031) and 15 feature stills miss the thresholds.
- **Canvas.** Remotion draws canvases on the GPU with either `gl`: in software, Rive measured 37.3 dB (8 stills under 40 dB), the HTML-in-canvas transitions 33.6 dB at worst, GIFs 52.6 dB; on the GPU they are identical or above 50 dB. Lottie's canvas renderer came closer in software (60.1 dB against 47.4). Determinism under load (24 busy processes of the measurement, load 34 to 90): 2 of 1,080 transparent frames differed with the GPU canvas, 0 of 1,140 in software; at low load none differed in any combination. A heavy canvas (4,000 particles, 60 transparent frames) took 102 to 133 s on the GPU against 7 to 13 s in software, and under load a GPU canvas frame exceeded the 35 s watchdog. Under software compositing (opaque captures with the CPU raster) both canvas modes draw identical pixels (5 fixtures), so those captures get no canvas flag.
- **Speed.** The GPU raster makes opaque captures composite on SwiftShader: the benchmark's Motio side took 4.36 / 4.16 / 4.36 s against 1.96 / 1.52 / 1.69 s at concurrency 1, 4 and 8, and `make bench --assert` fails. Transparent captures took up to 2 times as long. With the shipped defaults `make bench --assert` passes at low load: 0.30 / 0.62 / 0.88 and 0.29 / 0.61 / 0.86 of Remotion's time.

Implemented: `raster: "cpu" | "gpu"` and `canvas: "software" | "gpu"` on every render function and chunk worker, `--raster` and `--canvas`, `browser.raster` and `browser.canvas` in `motio.config.ts` (the flag wins; no `MOTIO_*` variable, since they are project choices). Defaults: `cpu`, or `gpu` when `chromiumOptions.gl` is explicitly `"swangle"` (from the option, `--gl`, `MOTIO_GL` or either config file) and `raster` is unset, so a project gets the pixels Remotion gives with the same setting, at the cost of slower videos; `canvas: "software"`. Hardware GL keeps Chrome's choices unless an option is set. `graphics-modes.integration.test.ts` checks each combination against Chrome's own feature report and the browsers a render launches. `check determinism` reads where each frame's canvases are when canvases are drawn on the GPU, and names the cause `canvas` with a suggestion of `--canvas=software` when every difference lies inside one. The parity suites render with the setting their references were recorded with (`gl: "swangle"` for the WebGL fixtures, `canvas: "gpu"` for Rive, GIF and the HTML-in-canvas transitions); the M4 suite already passes `gl: "swangle"`, so its 21 `knownMismatch` and 6 `knownFlickerMismatch` markers were removed after a run in which all of them passed. ## D-090 The open points of the virtual time model: transitions, the time zone and the language, animation-frame and timer loops, the hint (2026-11-25, closes D-086)

- **CSS transitions.** A transition starts when a style changes, so it depends on the frame before. In the virtual time model every page steps through every frame from 0, so the frame a transition is first seen on (the frame whose render, timers or settling changed the style) is the same on every page: it is seeked from there, scaled by the sequence's rate like keyframes. The second seek of a frame, after settling, now runs on warm-up steps too, or a transition started while settling would start one frame later on a page that only stepped through that frame. In the frame model no such frame exists (a new page shows the changed style without a transition), so a transition is seeked to its end, as a new page shows it, with a `W_CSS_TRANSITION` warning that names the virtual model; before, transitions were seeked from the start of the sequence, which played part of a transition that started early in a sequence and skipped later ones. On a box moved at frame 10 with a 1 s linear transition: in the virtual model x is 200·(f−10)/30 at frame f, identical at concurrency 1, 4, shuffled and with a page per frame; in the frame model x is 200 from frame 10.
- **Time zone.** Renders set the page's zone with `Emulation.setTimezoneOverride`, `UTC` by default on every machine; `timeZone` on every render function and `selectComposition`/`getCompositions`, `--time-zone`, `browser.timeZone` in `motio.config.ts` (a project choice, so no `MOTIO_*` variable; the machine's zone is one `Intl` call away in the config). Applied in both models, since local-time code reads the zone in either, and so the chunks of a distributed render on machines in different zones agree. Checked: the page, a dedicated worker and pages sharing a browser at concurrency 4 report the zone given. The preview and the Player keep the viewer's zone. The locale (`navigator.language`, `Intl`'s default) is still the machine's.
- **Animation-frame loops in the frame model.** D-086 blamed the settle loop; measured, the page settled in under 1 ms and `Page.captureScreenshot` waited instead (up to 7.6 s), because renders run Chrome without its frame rate limit and the loop drew a canvas as fast as Chrome could. Before: the virtual-time fixture with a GPU canvas took 203 s for 20 frames, and 38 s for 60 frames at concurrency 4 with the default software canvas; a fixture without the canvas loop was not affected. The renderer now injects an animation-frame gate in the frame model: page callbacks run while `seek` renders and settles; at its end the callbacks already requested run in one more animation frame (at most 100 ms) and the ones they request wait for the next `seek`. Cancelling those requests instead left every capture waiting about one frame interval (18 ms against 1 ms). After: 0.8 s for the 20 GPU-canvas frames, 0.8 s for the 60 frames at concurrency 4, 0.6 to 1.2 s for 60 frames at concurrency 1 (0.8 s before); the frame-driven fixture is unchanged. The loop's pixels stay non-deterministic, which is what the frame model says of clock-driven code; a callback that asks for the next frame 30 times in a row is reported as `W_ANIMATION_FRAME_LOOP`. Timers (`setTimeout(0)` loops) are not gated.
- **The hint.** When `check determinism` runs in the frame model (flag, config, else the composition's model), finds differences and the pages reported `W_ANIMATION_FRAME_LOOP` or `W_MATH_RANDOM`, it appends the virtual model to the diagnosis (`--time-model=virtual`, with `--reference=fresh` to check it) and adds `diagnosis.timeModel: { suggested: "virtual", evidence }` to the JSON. The cause stays the one the run pattern gives. On the fixture in the frame model: cause `random`, evidence both codes.
- **Timer loops in the frame model** (added after the first round). Measured on a fixture with a `setTimeout(0)` chain that moves a box and redraws a canvas and a 1 ms `setInterval` that updates React state: before, every configuration failed with `E_SEEK_TIMEOUT` (35 s per attempt); the chain's DOM changes alone did it, since the settle loop and the chain both ran every 4 ms and two yields without changes never came. The canvas alone and the interval alone rendered (0.4 s for 10 frames), and a timer loop drawing a canvas, even on the GPU, did not slow the capture as the animation-frame loop did (timers are clamped to 4 ms). The gate now also wraps `setTimeout` and `setInterval` (never `MessageChannel`, `queueMicrotask` or `Promise`): timers that come due between seeks are held and run when the next seek starts, an interval once; the runtime's own timers bypass it; 30 chained calls or interval firings in a row are a loop, reported as `W_TIMER_LOOP` and named by `check determinism` with the other clock evidence. The settle loop drops the DOM changes made inside an iteration of a detected loop and, with a loop detected and no handle open, stops waiting for a quiet DOM after 8 changing yields: React commits the interval's state in a later task, which cannot be attributed to the timer, and the chain plus the interval still timed out without this bound. After: 0.5 s for 20 frames, 0.8 s for 60, 0.6 s for 60 at concurrency 4, 0.95 s for 20 with GPU canvases; the frame-driven fixture and the clock-driven one are unchanged. In the virtual model the same chain ran forever at one instant (`more than 100000 timers ran for one frame`); the shim now clamps timeouts nested more than five levels deep to 4 ms, as browsers do, and the fixture renders 60 frames in 0.6 s, identical with a page per frame.
- **Language** (added after the first round). `navigator.language`, `navigator.languages`, `Intl`'s default locale and `Accept-Language` followed the machine. Renders now pin them, `en-US` by default (the language the docs and examples assume, and the one Chrome reported on this machine without an override), with `locale` on every render function and `selectComposition`/`getCompositions`, `--locale`, `browser.locale` in `motio.config.ts`, no `MOTIO_*` variable, passed to chunk workers. `Emulation.setLocaleOverride` covers `Intl` (in workers too) and the page's `navigator.language`; `Emulation.setUserAgentOverride` with `acceptLanguage` covers `navigator.languages` and the header (one override, with the `userAgent` option when set, so two do not compete); workers' `navigator.language` followed neither, nor `--lang` or `LANG`, but follows the launch flag `--accept-lang`, which joins the browser pool key (`openBrowser()` starts its browser with the default locale, so default renders keep using it). Checked against an echo server: default `en-US` everywhere, `de-CH` everywhere when given (`1'234.5`), also with a custom user agent.
- **Preview and Player.** They keep the real clock: making clock-driven code follow scrubbing would mean installing the shim in the viewer's page and replaying from frame 0 on every seek backwards, which the Player's real-time playback cannot afford. Documented as a limit in the guide.

Open: measured on macOS only; a `puppeteerInstance` keeps the language its browser started with in dedicated workers.

## D-091 Composited on SwiftShader, tiles are rasterised with one copy and reuse textures only at their size; `check determinism` names Chrome's image cache (2026-11-25, closes the determinism points of D-088)

The determinism points left by D-088 were measured on the M4 compositions that failed `check determinism --reference fresh` (14 in Remocn and snapcn), with the default CPU raster, and with a probe rendering each window three times on a new page per frame, twice ascending and once descending. They come from four causes, not three; each was isolated on a minimal composition and located in Chromium's source (BSD, outside the clean room).

- **Tiles holding another tile's content** (snapcn `card-rail`, a rail of cards tilted under `perspective`). On transparent captures some frames showed whole 256 px tiles of a card, bent by the perspective, with the next card's content, on different frames in every run and even between two runs with a new page per frame; JPEG never. Cause: on macOS Chrome rasterises tiles straight into buffers that SwiftShader reads while compositing (zero-copy raster), and the capture can see a buffer holding another tile. `--disable-zero-copy` (one-copy raster: a staging buffer copied into the tile, what Chrome does on Linux anyway) removes it: 0 disagreeing frames in 4 series of 10 frames against 0 to 7, and `check determinism` on frames 49-58 passes 4 times in 4 against 4 failures before.
- **Tile textures reused at a larger size** (jitter-lab "in", in both entries; the ±1 levels on `bloom-lockup`'s photos; `OpusSplit`; `roster-grant`). Isolated on jitter-lab's line under `rotateY(0.001deg)`: only GPU compositing shows it (JPEG, and PNG with `--disable-gpu-compositing`, are clean, with the CPU or the GPU raster alike); it lives in the renderer process (descending with a new page per frame on the same browser is clean); it survives hiding the document with `display: none` for three frames, so neither the layers nor their raster scale carry it; it needs four or five earlier frames drawn larger. cc's `ResourcePool` gives a tile any free texture up to twice its area (`ResourceMeetsSizeRequirements`) unless Chrome runs with `--disallow-non-exact-resource-reuse`, and a page that drew larger frames has larger textures free. With the switch every case above passes. That SwiftShader then samples the tile a level apart (through other texture coordinates) is inferred from the fix, not traced. This was D-088's "raster scale kept from an earlier frame": the raster scale is not it, and the `display: none` reset did not fix these cases here.
- **Chrome's image decode cache** (`moodboard-reveal`, `logo-assemble`: D-088's "remote photos"). 16,000 to 24,000 pixels of one photo differ, 84 to 98% of them by at most 2 levels, in both compositing modes. cc's `SoftwareImageDecodeCache` draws a downscaled image from a decode at a mip level, which it builds from the smallest cached decode at least that large that it can still lock (one left by an earlier frame at another size), else by decoding to scale (JPEG) or from the original: the source, and the pixels by a level, follow the frames drawn before and what the memory system purged. Remote has nothing to do with it: a local photo shrinking across mip levels differs on frames 13-14 of ascending runs every time. The cache is cleared only on a cross-document navigation (`LayerTreeHost::SetSourceURL`) or with a new compositor frame sink; `Memory.simulatePressureNotification` (critical), Skia cache limits and `decode()` on every image before the capture changed nothing, and the GPU raster is worse (three new pages per frame disagree among themselves on `moodboard-reveal`). It cannot be removed from outside Chrome, so `check determinism` names it: cause `image` when, in every differing frame, at least 90% of the differing pixels lie inside `<img>` elements drawn smaller than their natural size and at least 75% differ by at most 2 levels. The JSON gains `faintPixels` and `imagePixels` per mismatch; `renderFrames` gains `onImageRegions` (Motio extension).
- **OpusSplit** passes in some runs only because of Motio: the frames that failed determinism (171-175) are ±1 levels on a few pixels of the gallery photos at the start of its sequence, the second cause above, and pass with the fix. Its still failure (39.94 dB) was the CPU/GPU raster difference D-089 closed; a flicker failure on frame 270 (34 dB against Remotion, one run on 2026-11-24) did not reproduce in three runs.

Applied where Chrome composites on SwiftShader (transparent captures with the CPU raster, and the GPU raster): `--disable-zero-copy` with the CPU raster, `--disallow-non-exact-resource-reuse` in both; opaque captures composite in software and get neither, and hardware GL keeps Chrome's choices; `chromiumOptions.flags` can undo either. Cost: transparent captures took 10 to 22% longer on three M4 compositions (90 frames, three alternating rounds, load 6 to 7; one outlier at 75%); opaque videos are unchanged, and `make bench` captures JPEG. After: 6 of the 10 measured failures pass (`card-rail`, both "in", `bloom-lockup`, `OpusSplit`, `roster-grant`), `moodboard-reveal` and `logo-assemble` are named `image`. `settling-text-3d`, lines of text on 3D-transformed layers settling into place, joins D-074's suite in PNG: 46 of 60 frames differed without the switches, 0 with.

Open: `paper-tear` (frames 54-56, 13 to 32 pixels by one level, GPU compositing only; frames 59-60, the edge of a flying scrap, in both modes) and `orbit-gallery` (frames 147-149, 8 to 22 pixels by one level) still differ in ascending runs, reported as `raster`; the GPU raster draws photos differently even on new pages, which the M4 stills (recorded and compared with `gl: "swangle"`) are exposed to; the local fixture did not reproduce the zero-copy tiles, so only `card-rail` covers them. Measured on macOS only.

## D-092 The first npm release: lockstep 0.1.0, trusted publishing from a tag (2026-11-25)

The author chose the GitHub repository `essedev/motio`, the site `https://motio.esse.dev`, the `@motiojs` scope plus the unscoped `create-motio`, one version for every public package starting at 0.1.0, and npm's trusted publishing (OIDC) for releases.

- **What is published**: the 37 packages of `packages/` that are not private; `@motiojs/testing` stays private, since only `devDependencies` name it. Each carries `repository` (with `directory`), `homepage` (its site page when it has a README, else the site), `bugs`, `publishConfig.access: "public"`, a copy of the root LICENSE and its own NOTICE (the CLI's names the Inter font of the `basic` starter), because Apache-2.0 asks redistributions to carry both and npm packs only a package's own LICENSE. Node-only packages declare `node >=22`. `tools/release/release.test.ts` checks all of it, the lockstep version against core's `VERSION`, and the publish order.
- **How**: `.github/workflows/release.yml` runs on a `v*` tag (or by hand, dry run by default): Node 24, npm 11, pnpm from `devEngines.packageManager`, install, lint, build, unit tests, then `tools/release/publish.ts`. The script packs every package with `pnpm pack` (it applies `files` and turns `workspace:` ranges into the version), checks each tarball (version, no `workspace:`, `link:`, `file:` or `catalog:` range, LICENSE and NOTICE present) before publishing anything, then publishes each tarball with `npm publish` in dependency order, skipping versions npm already has, so a rerun finishes a partial release. `pnpm publish` was not used: pnpm's docs say it attaches provenance under trusted publishing but name no version that supports it, while npm documents the whole flow (npm 11.5.1 or later); npm attaches provenance by default under trusted publishing, and the workflow sets `NPM_CONFIG_PROVENANCE=true` so a run without it fails. Prereleases go to the `next` dist-tag.
- **First publish**: npm configures a trusted publisher only for an existing package, so 0.1.0 is published once from a fresh clone with a short-lived token in `NPM_TOKEN` (the same script; npm reads the token through a `${NPM_TOKEN}` reference in a temporary npmrc, so it never reaches the disk or the log), then `tools/release/trust.ts` runs `npm trust github <package> --repo essedev/motio --file release.yml --allow-publish` for every package (npm 11.15.0 or later per npm's docs, not 11.10; npm keeps one trusted publisher per package, so a package trusting something else is reported and left alone). Steps in `CONTRIBUTING.md`.
- **Source maps carry their sources** (`inlineSources` in `tsconfig.base.json`). Found by installing the packed packages into a project outside the repository: maps pointed to `../src`, which is not published, and the first `motio dev` printed one Vite warning per Motio module (113 for the `basic` starter); `make try` had the same defect, unseen because the init integration test did not read the dev server's output (it does now). The packed packages grow from about 3.3 to 4.3 MB in total. Declaration maps still point to missing sources; editors then fall back to the `.d.ts`.
- **`@motiojs/ffmpeg`**: `RELEASE_OWNER` is `essedev`, and whether the release is published is now its own constant, `RELEASE_PUBLISHED` (false): the old check took "owner is not the placeholder" to mean "archives published", which would have sent downloads to a release that does not exist yet, with digests of local builds. The package goes out at 0.1.0 with the others and falls back to the FFmpeg on `PATH` until the FFmpeg release and a Motio release with its manifest (D-065).
- Left for after the publish: `NPM_PUBLISHED` and the "not on npm yet" wording (a patch is prepared outside the repository), READMEs for 25 packages, the size of `@motiojs/google-fonts` (39 MB unpacked). Revisit: tests on GitHub's runners (only lint, build and unit tests run in the release job; there is no CI workflow for the full suite).
