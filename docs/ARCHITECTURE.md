# Architecture

Status: accepted for implementation, 2026-11-22. Revised after an adversarial review and the time-model spike (see `DECISIONS.md`). The project is called Motio: the `@motiojs/motio` package is the entry point (the equivalent of `remotion`, D-081, since npm refused the unscoped name), and the other packages live under `@motiojs/*` too because the `@motio` scope is taken on npm.

## What this is

An open-source framework for making videos with React. A video is a React tree that is a pure function of the frame number. The engine renders it in a real headless Chrome, captures it one frame at a time and encodes it with FFmpeg.

The public API is compatible with Remotion's documented API, so existing Remotion projects can move over by changing their imports, or with no change at all through the bundler alias. The engine is written from scratch: it uses Remotion's documentation and observable behaviour, never its source code.

**Compatibility target: `remotion@4.0.545`.** Every "compatible" claim refers to this version. `compat/manifest.json` lists each public symbol of the target (package, symbol, props or options, tier, status: supported, approximated, stubbed, missing). The manifest drives `doctor`, the stubs and the compatibility tests, and moving the target is an explicit change that re-records the oracle. Since D-066 the target moves on a schedule (every few months or at a significant Remotion release), not with every release, and missing symbols are added when a real project needs them.

## Goals

1. **Fidelity.** The pixels are the ones Chrome draws. There is no reimplementation of CSS, layout or text: if it looks right in Chrome, it renders right.
2. **Determinism.** The same project, props and frame number give the same pixels, on every run and in any order. Across machines the guarantee holds for the same OS, CPU architecture and container image with the pinned Chrome and software GL; macOS and Linux, or arm64 and x64, are never expected to match. Enforced by tests on decoded frame hashes, never on encoded files (x264 output depends on its thread count).
3. **Compatibility as an entry point.** Remotion's public API, in tiers (see "API surface"), checked against values and frames recorded from the published package. Since D-066 it is a layer kept stable, not the goal: work is chosen by what someone needs to use Motio without knowing Remotion, and where Motio can do better it designs its own API and maps Remotion's on top (`@motiojs/text`).
4. **Agent-first tooling.** Every command has machine-readable output (`--json`, validated against a published schema), errors with stable codes, and commands that let an agent check its own work without watching a video: stills, contact sheets, flicker and determinism checks, a compatibility report.
5. **Complete for most use cases.** Data-driven videos at scale, captions, social clips, product demos, audio visualisers, embedded players and video editors built on the Player, automated and distributed rendering.
6. **Free for any use.** Apache-2.0, no per-render or per-seat fee, including distributed rendering and embedding the Player in a product.

## Non-goals for v1

- **A Studio editor.** A `dev` preview page built on the Player covers watching motion while editing (see "Preview"). Prop forms, timelines and render queues serve people who do not write code, and can be built on the Player later.
- **A browserless renderer.** The opposite trade-off (speed over fidelity), already explored by other projects.
- **Client-side rendering with WebCodecs.** Dropped from the plan (D-066).
- **A hosted cloud service.** Distributed rendering ships as a library and adapters for the user's own infrastructure.

Rules that follow from this:

- Ported code keeps its copyright header, the original licence and an entry in `NOTICE`, and says what was changed (Apache-2.0, section 4).
- Nobody working on this project reads Remotion's source, its type declarations (`.d.ts`) or its source maps. The oracle installs Remotion in `tools/oracle/`, outside the workspace and excluded from search and lint, and only calls its public API.
- Docs prose, type signatures and error or warning messages are not copied word for word; the API shape and behaviour are reproduced (which inputs fail, with which error class), the text is ours (D-054). "Remotion" appears only as nominative compatibility wording.
- Oracle recordings are produced by the project author as an individual, for this personal open-source project, under Remotion's free licence for individuals, at the pinned version. Recording on behalf of a company would need a Remotion company licence.

## The page and the frame protocol

The renderer serves the built bundle over HTTP from a local server (ES modules do not load from `file://`). Before any page script runs, `Page.addScriptToEvaluateOnNewDocument` injects the run context: input props, environment variables, the protocol version, the frame seed, the time model and, in the virtual time model, the clock shim, in the frame model the animation-frame gate (both top frame only: nothing advances an iframe's clock). `Emulation.setTimezoneOverride` sets the page's time zone, `UTC` unless the `timeZone` option names another, so `Date` and `Intl` read the same on every machine and in every chunk; dedicated workers follow it. `getInputProps()` can therefore be called at module top level.

**Bundle layout.** A user project has an entry file that calls `registerRoot(Root)`, where `Root` renders `<Composition>` and `<Still>` elements (the Remotion convention; the entry is found from the CLI argument, the config's `entryPoint`, or `src/index.ts(x)`). `@motiojs/bundler` builds with Vite a page whose module script imports the user entry and then calls `mountPage()` from `@motiojs/core/runtime`. `mountPage()` reads the run context, collects the registered compositions by rendering `Root` in collection mode, mounts the selected composition on `setComposition`, and installs the page API below. The output directory (`index.html`, assets, and the project's `public/` folder copied to `<outDir>/public`) is the `serveUrl` the renderer serves. Before the user entry runs, the page sets `globalThis.__motioBundle = { publicPath, staticBase, staticFiles, env }`, which `staticFile()`, `getStaticFiles()` and `process.env` read (`process.env` in user code is compiled to the `__MOTIO_ENV__` global; variables the renderer injects at run time win over build-time ones). `mountPage()` mounts into `#motio-root`. Like Remotion's Node API, `bundle()` reads no config file: the CLI loads `motio.config.ts` (or `remotion.config.ts`), applies the `MOTIO_*` variables over it and passes the values in, and a script that wants the same settings calls `loadConfig()`. The types of `motio.config.ts` live in `@motiojs/core/config` (types only, re-exported as `@motiojs/motio/config`) so that the config file loads without React; the schema that validates it lives next to the loader in `@motiojs/bundler`.

The page installs one versioned global:

```ts
window.__motio = {
  protocol: 1,
  getCompositions(): CompositionInfo[];
  setComposition(id: string, props: unknown): Promise<ResolvedComposition>; // runs calculateMetadata
  seek(frame: number): Promise<FrameReport>; // resolves when the frame is ready to capture
  cancelled?(): PageError | null; // the cancelRender() error, if any
  pending?(): PendingHandle[]; // open readiness handles, answered without waiting for a seek
  timeModels?: TimeModel[]; // ["frame", "virtual"]; absent in bundles built before the virtual model
  advance?(frame: number): Promise<void>; // virtual model: step the clock up to frame, unreported
};
```

The renderer refuses a bundle whose protocol version it does not speak, with an error that names both versions.

`seek(frame)` does, in order:

1. In the virtual time model, sets the clock to the frame's time.
2. Renders the React tree for the frame inside `flushSync` and writes the frame number to `document.documentElement.dataset.motioFrame`. Passive effects of a sync render run before `flushSync` returns.
3. In the virtual time model, runs the timers and `requestAnimationFrame` callbacks due up to that time, each inside `flushSync`.
4. Seeks every CSS and Web Animation (`document.getAnimations()`), paused, to the time elapsed since the start of the nearest enclosing `Sequence`, read from a `data-motio-from` attribute that `Sequence` writes on its wrapper. This is deterministic in any order and needs no clock shim. CSS transitions are the exception, since they start when a style changes: in the virtual time model a transition is seeked to the time since the frame it was first seen on (every page steps through every frame from 0, so that frame is the same everywhere); in the frame model, where a new page shows the changed style without a transition, it is seeked to its end and reported once (`W_CSS_TRANSITION`). The seek runs again after settling, on warm-up steps too, so a transition started while settling starts on the same frame on every page.
5. Settles: loops on real macrotasks until no readiness handle is open, no DOM mutation happened for two consecutive yields (MutationObserver), no `Suspense` fallback is mounted (the root boundary's fallback holds a readiness handle while mounted), `document.fonts.ready` resolved and every new image decoded. Updates scheduled on non-sync lanes (state set in effects, transitions, deferred values) are processed by React's own scheduler during these yields.
6. Returns a report: the frame number read back from the DOM, warnings (a font fell back to a system font, a handle was slow, `Math.random()` was called while the frame rendered, and those components report to the page's warning registry, such as a `staticFile()` whose case differs from the file or a `<TransitionSeries>` shorter than the composition), the audio intents active on the frame, timings. The renderer collects the warnings of every page, each once with the first frame it was seen on, into the render result.

Readiness handles carry a label and a timeout measured on real time. While a page call runs, the renderer asks `pending()` (answered at once, not queued behind the seek) every 5 seconds and reports each open handle through `onDelayRenderPending`. On timeout `seek` rejects with the label and the frame. A missing asset fails with its own code (`E_ASSET_NOT_FOUND`, `E_FONT_LOAD`) carried by the error passed to `cancelRender()`: `<Img>` checks the status of a failed load and does not retry a 404; a font that fails at module level fails the frames, not the listing of compositions. Stacks of errors from the page are mapped in Node through the bundle's source maps, and the first frame in the project's code becomes the error's `details.source`. The renderer applies the documented `retries` behaviour: it closes the page, opens a fresh one and retries the frame. A watchdog in Node bounds every `seek` independently of the page, so a busy loop in user code cannot hang the render. `pageerror`, unhandled rejections and console output are forwarded to `onBrowserLog` and surface as errors with codes; `cancelRender` fails the render with the given error.

Frames are indexed absolutely from the first frame of the composition, so any page or worker can render any frame and completion order does not matter. Render bundles use React's production build, so StrictMode double effects never leak handles.

## Time

Two models, measured by the spike (see `DECISIONS.md`, D-005):

1. **Frame model (default).** `useCurrentFrame()` is the only source of truth, as in Remotion. No clock is patched. CSS and Web Animations are still seeked by `seek` step 4. Any frame can be rendered in any order on any page. The spike showed frame-driven components, state set in effects, CSS keyframes and Web Animations all give identical pixels across sequential, reverse, shuffled and fresh-page orders in this model. Renders run Chrome without its frame rate limit, so a `requestAnimationFrame` loop on the real clock calls back as fast as Chrome draws: a canvas loop on the GPU made each screenshot wait about 10 s for its frame (and about 0.6 s at concurrency 4 with the default software canvas). The animation-frame gate (`frame-gate.ts`, injected by the renderer) wraps `requestAnimationFrame`: callbacks run while `seek` renders and settles; when `seek` ends, the callbacks already requested from Chrome run in one more animation frame and those they request are held until the next `seek` opens the gate (a request left pending, or cancelled, while the renderer captured made every capture wait about one frame interval, 18 ms against 1 ms). Timestamps stay real; nothing else is patched. The fixture then renders 20 frames with a GPU canvas in 0.8 s instead of 203 s, 60 frames at concurrency 4 in 0.8 s instead of 38 s. A callback that asks for the next frame 30 times in a row is reported as `W_ANIMATION_FRAME_LOOP`, and `check determinism` names it, with `W_MATH_RANDOM`, when it suggests the virtual model.
2. **Virtual model (opt-in).** For code that reads the clock instead of the frame (GSAP-style timelines on `requestAnimationFrame`, Lottie in clock mode, canvas loops, `setInterval` counters, `Date`-based motion), a shim makes `Date`, `performance.now`, `setTimeout`, `setInterval`, `requestAnimationFrame` and `Math.random` (reseeded per frame from the frame and `frameSeed`) follow the frame time. Chosen per render with `timeModel: "frame" | "virtual"` (`--time-model`, `render.timeModel` in `motio.config.ts`), else by the composition (`<Composition timeModel="virtual">`, carried in `CompositionInfo` and `VideoConfig.timeModel`), else `frame`. Listing compositions always uses the frame model.

   State accumulated by timers depends on history (a counter driven by `setInterval`, a ticker that sums the time between animation frames, particles integrated per frame), so stateless clock reads are not enough. The rule is that **virtual time only moves forward, one frame at a time, from frame 0, on every page**: a page asked for frame `n` first steps through every frame it has not rendered yet (`seek` steps 1 to 5 for each, warnings dropped), so its state is the state of one ascending render whatever frame it starts at. The renderer drives it: `RenderPage.seek` warms a page up through `advance()` in calls of at most 30 frames (`VIRTUAL_STEPS_PER_CALL`), so each call stays within the watchdog; a frame at or before the page's last one closes the page and opens a new one (the page rejects it too); pages are not recycled by default (`defaultRecycleEveryNFrames`), and a crashed page's replacement warms up like any new page. Chunks and distributed workers need nothing else: a chunk's pages warm up from frame 0 to the chunk's first frame. The pool keeps its shared ascending queue (each page then steps through about every frame), rather than contiguous ranges per page, which would leave far-ahead frames waiting in the reorder buffer of a video render. `check determinism --reference fresh` is meaningful as is: a new page per frame warms up from frame 0, which is the reference semantics, so it equals one ascending render exactly when the model holds. The page and its tests are in `mount-page.tsx` (`mount-page-virtual.test.tsx`); the integration tests (`packages/cli/src/virtual-time.integration.test.ts`, `packages/distributed/src/virtual-time.integration.test.ts`) render a fixture with all five kinds of clock-reading code and compare a single ascending render with a new page per frame, descending and random orders at concurrency 1, 4 and 8, frame ranges starting mid-composition, recycled pages and four distributed ProRes chunks (0 of 60 frames differ in every run; removing the warm-up makes 59 of 60 differ).

   Cost: a page renders every frame up to its last one, so time grows with the position in the composition rather than with the frames rendered, and concurrency helps less. A warm-up step is a seek without capture (about 1 ms for 24 animated boxes at 1080p, against 13 ms for a capture), so on frame-driven content at 1080p, 300 frames, h264, the virtual model took 1.00 to 1.02 times the frame model's time at concurrency 1, 1.09 to 1.18 at 4 and 1.07 to 1.14 at 8 (two alternating rounds, load average 7 to 11; `packages/cli/test-fixtures/virtual-time/src/cost.tsx`). Heavier trees make steps dearer; a still or a chunk at frame `n` costs `n` steps; a new page (each backward seek of a descending `check determinism` run, a crash retry) costs about 350 ms before its warm-up. The capture path is the same in both models. Before the animation-frame gate, a `requestAnimationFrame` loop left running on the real clock (in the frame model) kept Chrome drawing unthrottled frames: on the same content it raised the capture from 13 to 18 to 20 ms per frame.

Shim rules: installed before any page script; never patches `MessageChannel`, `queueMicrotask`, `Promise`, `setImmediate` or `crypto.getRandomValues` (reseeding it would make id generators collide); keeps private references to the real timers, which the engine uses for readiness timeouts and settling. User timers do not advance while `seek` waits for readiness; code that waits on a timer before `continueRender` must use the frame model. Workers, iframes and `OffscreenCanvas` are outside the shim and documented as such; state kept outside the page (`localStorage`, IndexedDB, the HTTP cache) survives a new page and is not reset. The Player and the preview never install it: there, clock-driven code runs on the real clock and does not follow scrubbing, a documented limit (D-090), and the time zone is the viewer's.

## Capture

- **Browser.** `chrome-headless-shell` from Chrome for Testing at a pinned version (Linux x64 and arm64, macOS x64 and arm64), downloaded by `browser ensure` and verified against SHA-256 digests committed in the repo, because Chrome for Testing publishes none. Driven over CDP with `puppeteer-core`.
- **Flags** for identical pixels: `--font-render-hinting=none`, `--disable-lcd-text`, `--force-color-profile=srgb`, `--force-device-scale-factor=1`, `--disable-skia-runtime-opts`, `--disable-checker-imaging`, anti-throttling flags, `--disable-frame-rate-limit`, software GL through ANGLE and SwiftShader by default: opaque captures composite in software (`--disable-gpu-compositing`), transparent ones rasterise on the CPU and composite on SwiftShader (`--disable-gpu-rasterization`), which reproduces Remotion's pixels with its default `gl`, the faint alpha of antialiased edges included (D-041). Hardware GPU is opt-in and gives up cross-machine identity.
- **Raster and canvas** (`raster`, `canvas`; `--raster`, `--canvas`; `browser.raster`, `browser.canvas`). Remotion's pixels depend on its `gl`: its default gives the CPU raster's pixels, `gl: "swangle"` the GPU raster's (SwiftShader), each identical on the M1 stills. `raster: "gpu"` drops `--disable-gpu-rasterization` and, for opaque captures, `--disable-gpu-compositing`, so they composite on SwiftShader (about 2.5 times slower on the benchmark); it is selected by an explicit `gl: "swangle"` unless `raster` is given (`resolveRasterMode`). `canvas: "software"`, the default, adds `--disable-accelerated-2d-canvas` wherever Chrome composites on the GPU (transparent captures, the GPU raster): Chrome's GPU canvas differed in 2 of 1,080 frames under heavy load and was 8 to 17 times slower on a heavy canvas, the software one differed in none; `canvas: "gpu"` reproduces Remotion's canvas pixels. Under software compositing both modes draw identical pixels, so opaque CPU-raster captures get no canvas flag. Hardware GL gets these flags only when the option is set. Every combination's effect is checked against Chrome's own feature report (`graphics-modes.integration.test.ts`). Wherever Chrome composites on SwiftShader, tile textures are reused only at their exact size (`--disallow-non-exact-resource-reuse`: a larger texture left over from a larger frame drew text and photos a level apart), and the CPU raster draws tiles with one copy (`--disable-zero-copy`: on macOS a capture could show a tile holding another tile's content) (D-091).
- **Two capture paths.** `Page.captureScreenshot` always works, is the reference path and the default (`auto`). With frames drawn unthrottled (`--disable-frame-rate-limit`) and opaque captures composited in software, it captures a 1080p frame in about 10 ms on one page (D-041), as fast as BeginFrame, and pages can share a browser (D-042, D-043). BeginFrame (`--enable-begin-frame-control`, `--deterministic-mode`, Linux only, not officially supported by Chrome) is deprecated (D-078) and stays available until a future release as `captureMethod: "begin-frame"`, with a one-time `DeprecationWarning`, with identical pixels (D-013, D-033) and one page at a time: above concurrency 1 it is refused (`E_BEGIN_FRAME_UNSUPPORTED`), because Chrome's display compositor can draw a page before its renderer delivered the frame (D-075). Before the screenshot the renderer sends BeginFrames until a main frame ran with the document hidden, then until a main frame ran after it was shown and a later BeginFrame found nothing new to draw. Before every capture the page reads its layout and waits for the images, fonts and style sheets that requested. On a BeginFrame page the renderer drives the compositor: frames without display updates while a page call runs (so `requestAnimationFrame` fires), then a pre-frame that runs style and layout and a wait for the images, fonts and style sheets it requested, then the captured frame.
- **Raster reset.** Before every capture the renderer hides the document (`opacity: 0` on the root element, from an isolated world) until a frame was painted hidden, then shows it again, so the captured frame is rasterised as on a fresh page. Without it a frame depends on the frames the page rendered before: Blink skips the raster invalidation of a transform change below 0.01 px of translation or 1e-4 in the other matrix components and keeps the last rasterised transform as the reference, and Chrome keeps the raster scale of a `will-change: transform` layer. Content that was invisible on the previous paint is invalidated in full when it shows again. On a BeginFrame page the hidden frame is a frame without display updates. Transparent captures also add, while the frame is captured, a translucent 1 px square just below the viewport: Blink marks a layer opaque when opaque drawings cover it, also two that only meet at a fractional edge (the scenes of `slide()`), and Chrome then rasterises it without clearing its tiles, so an antialiased seam blends with whatever the reused tile memory held (transparent on a new page, an earlier frame otherwise). The square makes the layer reach past its opaque drawings, so it is not opaque and every tile is cleared; it lies outside the capture and is removed before page code runs again. Opaque captures draw the background below everything and need nothing; lowering the root element's opacity instead would also clear the tiles, but Chrome applies it when compositing when the document has composited layers, and writes alpha 254.
- **Format.** PNG for alpha and for lossless output; JPEG for opaque output. The default (`jpeg`, quality 80, as in Remotion) is confirmed by the capture benchmark.
- **Background.** `Emulation.setDefaultBackgroundColorOverride`: transparent black for PNG captures with alpha, opaque black for JPEG, so what a composition leaves undrawn is black in an opaque video, as in Remotion (D-050).
- **Codecs.** One table maps each `codec` to its encoder, container, CRF range, pixel formats and audio codecs (D-037): H.264 (MP4, MKV, TS), H.265, VP8 and VP9 (WebM, alpha with `yuva420p`), AV1 (MP4, SVT-AV1 or libaom, D-064), ProRes (MOV, alpha with 4444), GIF (palette built from the whole clip in a separate pass). The output's extension names the container and must be one the codec is written to, as Remotion checks it (H.264 to `.mp4`, `.mkv` or `.mov`, VP8 and VP9 to `.webm`, ProRes to `.mov` or `.mkv`, ...); any other fails before rendering instead of writing, say, WebM into an `.mp4` file. Image sequences are written by `renderFrames`.
- **FFmpeg.** The `ffmpegExecutable` option, else `MOTIO_FFMPEG`, else the pinned build of `@motiojs/ffmpeg` when installed, else `ffmpeg` on `PATH` (D-065). When the package is installed but its build cannot be downloaded (archives not published, no archive for the platform, network failure) and `ffmpeg` on `PATH` runs, the render uses it and reports `W_FFMPEG_FALLBACK`; a digest or verification failure is never papered over. Every render checks the version (5.1 or later, D-051) and the encoders its output needs before any page opens.
- **Transport.** Frames stream to FFmpeg's stdin (`image2pipe`) through a reorder buffer, with backpressure. No frame files on disk except for `renderFrames`.
- **Pages.** A session keeps a pool of browsers; by default a render's pages are spread over two browsers (more above concurrency 8, four pages each), `pagesPerBrowser` chooses another layout (D-042). A page is recycled every N frames (a new tab on the same browser) and on crash; a crashed page's frames are retried on a fresh page, on a new browser if the browser crashed. Browsers are launched detached, so the renderer kills the ones still running when the Node process exits, and when it gets SIGTERM, SIGINT or SIGHUP with no other listener (the signal is then raised again for its default action); a host that listens itself (the CLI cancels its render on Ctrl+C) handles the signal.

## Colour

RGB to YUV conversion is explicit, never FFmpeg's default (BT.601 for RGB input, full range for JPEG input):

- PNG frames (full-range RGB): `scale=in_range=pc:out_color_matrix=bt709:out_range=tv:flags=accurate_rnd+full_chroma_int`. JPEG frames (Chrome's full-range BT.601 YCbCr, 4:2:0): the `colorspace` filter converts matrix and range in YUV and keeps Chrome's chroma samples (D-040). Output tagged `-colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv`.
- Remotion's `colorSpace` option (`default`, `bt709`, `bt2020-ncl`) is matched against the oracle.
- `yuv420p` requires even dimensions; odd sizes are rejected with a clear error, as Remotion does.
- A colour test encodes a known palette, decodes it back and requires every patch within 2 code values, and checks the tags with `ffprobe`.

## Media

- **Media service.** The renderer starts a local HTTP service per session and passes its URL to the page (`RunContext.mediaBaseUrl`). It answers media information, the exact source frame for a time (selected from packet timestamps, extracted with FFmpeg, batched and cached in an LRU with request deduplication, D-015) and where a native element must seek to show a frame. Media on the bundle's origin is read from the bundle directory, other http(s) media through FFmpeg (D-030).
- **Embedded video.** `OffthreadVideo` shows the extracted frame (`floor` rule) in an `<img>`, the `@remotion/media` `Video` draws it into a `<canvas>`, and both hold a readiness handle until it is displayed. The HTML5 `Video` keeps the native `<video>`, seeked to the middle of the frame the `nearest` rule picks and awaited on `seeked` (D-016), so refs and canvas drawing work. In the Player every component plays a native element on the real clock, synchronised to the Player's frame, volume, mute and rate through `MediaPlaybackContext`; `Html5Audio` borrows the Player's shared audio tags (D-029). After a play request, and after buffering, the Player holds its frame until every playing media element advances, then starts its clock when the slowest one did and moves the faster ones back to it: an audio element's time stands still for the output device's start-up latency (a few milliseconds on built-in speakers, 250 ms or more on Bluetooth headphones), and a clock that started at once would run ahead of the sound by that much, below the drift that triggers a re-seek.
- **Audio.** Never captured from the browser. Each media component reports, on every frame it plays, the source position, rate, pitch, volume and stream (`FrameReport.audio`, protocol 2). The renderer collects them while capturing and seeks the frames the capture skips without capturing, so `frameRange`, `everyNthFrame` and audio-only codecs cannot drop audio; consecutive frames whose position advances by the rate form one segment. The mixer (`@motiojs/audio`) decodes sources to float PCM, applies sample-accurate offsets and per-frame volume in Node (D-014, D-028), and encodes once for the whole timeline, muxed into the MP4 in the same FFmpeg run or written alone for `mp3`, `aac` and `wav` (D-030). Pitch uses `asetrate` and `atempo`, available in common FFmpeg builds.
- **Fonts.** Loaded from files or Google Fonts and awaited before every frame. Text that fell back to a system font is reported.
- **Animated images** (`<img>` with GIF or WebP) run on real time in Chrome; `AnimatedImage` (core, `ImageDecoder`, D-071) and `Gif` (`@motiojs/gif`, decoded in JavaScript) are the frame-accurate components.
- **Preloading.** Renders wait for every asset and need none. In the Player, `@motiojs/preload` adds hidden media elements and `<link rel="preload">`; Chrome shares a media element's buffer with every element playing the same file, so the Player needs no code for it (D-070).
- **Node media functions.** `getVideoMetadata`, `extractAudio` and `getSilentParts` run ffprobe and FFmpeg on local files outside any render (D-068).

## Parallel and distributed rendering

- **One machine.** A pool of pages across browser processes (two by default, D-042) pulling frame numbers from a shared queue, all feeding one encoder. Default concurrency: half the CPU threads, capped at 8, as in Remotion.
- **Many machines.** `renderDistributed()` plans the timeline into chunks; workers run `renderChunk()` and encode each chunk on its own (MPEG-TS for H.264 and H.265, WebM for VP8 and VP9, MOV for ProRes), starting on a keyframe; meanwhile `renderAudio()` renders the audio once as float samples; the assembler concatenates without re-encoding (D-018) and encodes the audio in the same run, as `renderMedia` does (D-039). Workers implement one method, `ChunkWorker.renderChunk(job)` with a JSON job: `LocalChunkWorker` runs a child process per chunk, and Lambda, Cloud Run and Kubernetes are adapters to write.

## Preview

`motio dev [entry]` starts a Vite dev server (`startDevServer()` in `@motiojs/bundler`, with the settings of `bundle()` plus React Fast Refresh for the project's files) on `--port`, `Config.setStudioPort()` or 3000, and serves the `@motiojs/preview` page. The page renders the root with no composition selected, so every `<Composition>` registers as on the render page, and lists them; the selection lives in the URL hash. The selected composition plays in `<Player controls>` after core's `resolveComposition()` ran `calculateMetadata()` with the props from the JSON editor (checked against the schema, as warnings). Transport: play, scrub, step a frame or a second, jump to the ends, loop an in/out range, rate, zoom, frame counter and timecode (`HH:MM:SS:FF`), with keyboard shortcuts. Under the stage a timeline shows a row per sequence, labelled with its `name`: the page provides core's `SequenceRegistryContext` around the Player, and every `Sequence`, `Series.Sequence`, `Loop` and timed media component registers its placement in composition frames, also outside its range (renders provide no registry, so they pay nothing); its ruler scrubs with the pointer or the keyboard. The props editor flags keys that neither `defaultProps` nor the schema's object shape declares. A Problems panel lists what a render would trip on while the Player plays on: files that failed to load (element error events, and HTTP errors from the resource timing), `delayRender()` handles still open with their age and call site, a `cancelRender()`, and core's page warnings. Errors thrown by the composition are shown with their stack mapped through the dev server's inline source maps, the source around the throwing line, and the frames of React, Motio and other dependencies folded. A component edit hot-reloads in place; any other edit reloads the page, which restores the frame, range and props from `sessionStorage`. Build errors (a syntax error, an unresolved import) replace Vite's overlay: the page module mounts the preview first, forwards Vite's `vite:error` events, and imports the entry dynamically, so an error in it reaches the page; the terminal gets the message, file and code frame without Vite's stack. The page is responsive: under 1100 px the props and checks become a drawer, under 720 px the composition list too. The stage resets inherited CSS, so the composition lays out as on the bare render page.

"Render still" asks the dev server to render the current frame through the real pipeline (`motio still` semantics): the CLI hands the server a handler that rebuilds a production bundle after a source change, runs `selectComposition` with the page's props and `renderStill` as PNG. The page shows the image, can overlay it on the Player with a difference blend, and can save it to the project's `out/<composition>-<frame>.png` (the server copies its temporary file there). `--json` prints one object when the server listens (URL, port, entry, pid) and nothing after; SIGINT and SIGTERM stop the server and remove the session's files (D-026).

## Compatibility

- **Drop-in.** The `@motiojs/compat` Vite plugin resolves `remotion` and `@remotion/<pkg>` to our packages and fails the build on an unsupported package, with the package name and the alternative. `remotion.config.ts` loads through a `Config` object with the documented setters. Environment variables follow Remotion's rules (`.env` and `REMOTION_`-prefixed variables exposed through `process.env`) through Vite `define`; `MOTIO_`-prefixed variables are exposed too, except Motio's own tool settings (`MOTIO_FFMPEG`, `MOTIO_BROWSER_EXECUTABLE`, ...). `doctor` lists every symbol a project uses with its manifest status.
- **Proof.** For every pure function, fixtures record the outputs of the published package at the target version, produced by `tools/oracle`. For components, effects and templates, the oracle renders reference stills and videos, and ours must match within the thresholds in `ROADMAP.md`. Fixtures and goldens change only through an explicit record command, in separate commits that state why.

## Testing

- **Unit** (Vitest, Node): every pure function against the oracle fixtures.
- **Core components** (Vitest, jsdom): timeline semantics of `Sequence`, `Series`, `Loop`, `Freeze`, `useVideoConfig`.
- **Integration** (Vitest, serial, real pinned Chrome and FFmpeg): the frame protocol, frame-stamp fixtures (the frame number encoded as a pixel barcode, decoded from every captured frame), React fixtures (`delayRender` in an effect, `setState` in an effect, `useDeferredValue`, lazy and `Suspense`), colour, encoder output checked with `ffprobe`.
- **Golden frames**: fixture compositions and templates compared with the oracle (PSNR, SSIM) and with our own goldens.
- **Determinism**: `motio check determinism` renders a range in several orders and concurrencies and compares decoded frame hashes; with `--reference fresh` every run is compared with a render that uses a new page per frame (D-074).
- **Flicker**: `motio check flicker` flags frames that differ from both neighbours beyond a threshold.
- **Player**: jsdom component tests and real-browser tests in the pinned chrome-headless-shell driven by puppeteer-core: ref API, events, real-clock playback, buffering (D-022).
